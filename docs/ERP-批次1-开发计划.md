# 菜芦 ERP 开发计划（批次 1）

> 建立：2026-10-28 ｜ 状态：**设计完成，待启动开发**
> 关联文档：`docs/ERP-批次1-技术架构.md`（architect，2895 行）、`docs/ERP-批次1-产品需求PRD.md`（product-manager，2186 行）
> 本文是**启动开发时的总纲**，两份设计文档是细节依据。

## 一、项目目标（最终形态）

老大需求：在菜芦（Rust/alun 0.4.2 + Vue3 + TDesign）上建 **ERP**，含 4 个业务模块：

| 模块 | 范围 |
|---|---|
| **采购管理** | 采购申请 → 订单 → 收货 → 退货 → 应付 |
| **仓库管理** | 多仓库存、入出库、调拨、盘点、成本核算 |
| **销售管理** | 报价 → 订单 → 发货 → 退货 → 应收 |
| **财务管理** | **会计凭证**、总账、明细账、资产负债表、利润表、期末结账 |

**业务形态**：生产制造（需 BOM、领料、产成品入库）
**财务深度**：**专业会计凭证级**（科目表、借贷凭证、总账、报表、结账）
**库存粒度**：按 SKU 数量（不做批次/序列号）
**组织范围**：多仓库（含调拨）

**总量评估**：约 **11-15 周**（单人节奏）。

## 二、总体路线：4 批次，每批都能上线

| 批次 | 内容 | 价值 | 工期 |
|---|---|---|---|
| **1**（本计划） | 最小主数据 + 采购 + 入库 + 库存 + 应付 + **凭证引擎 + 总账** | 打通"采购→库存→账务"**垂直闭环** | 41 人日 |
| 2 | 销售 + 出库 + 应收 + 收款 + 客户信用 | 进销两头通 | ~3 周 |
| 3 | 生产：多层 BOM、工单、领料、产成品入库、委外 | 制造闭环 | ~3-4 周 |
| 4 | 资产负债表/利润表、期末结账、多仓调拨、成本精细核算 | 完整财务 | ~2-3 周 |

**为什么先做第 1 批的垂直闭环**：ERP 的命门是"业务-财务一体化"（业务单据自动生成正确凭证）。先把这条链打通，销售和生产都是同构复制，风险大幅降低。横向先做完所有主数据反而验证不到核心。

## 三、第 1 批范围（严格边界）

### 做
```
最小主数据：物料 · 供应商 · 仓库 · 会计科目 · 计量单位
业务链：采购订单 → 收货入库 → 库存增加（移动加权成本） → 应付账款 → 自动生成记账凭证 → 总账可查
辅助：会计期间（只做开启 + 禁止向已结账期间写凭证）、单据操作轨迹
```

### 明确不做（防止范围蔓延）
- ❌ 审批流（只留 `APPROVED` 状态与权限点）
- ❌ 销售 / 生产 / BOM / 调拨单
- ❌ 期末结账 / 报表 / 结转损益
- ❌ 付款单、发票、完整核销链路（本批只有应付单 + 手工核销标记）
- ❌ 出库业务（算法有设计，不在交付范围）
- ❌ 多币种汇率换算（只存 `currency_code`）
- ❌ 批次/序列号

## 四、六步实施计划（41 人日）

| 步 | 内容 | 交付物 | 验收标准 | 人日 |
|---|---|---|---|---|
| **①** | 主数据 + 科目 + 期间 + 取号 | `V0030`/`V0037` 迁移；`business/erp/{unit,warehouse,account,material,supplier}/`；`shared/{money,seq,period,doc_status}.rs` + 单测 | 5 个 CRUD 可用且权限码三方一致；科目树父子展开+末级校验；期间列表+开启；`cargo test` 全绿；`money.rs` 舍入/尾差分摊单测 ≥8 用例；迁移 `up→down→up` 可重复 | **5** |
| **②** | 采购订单 | `V0031`；`purchase_order/` | 主+明细一次提交、后端算金额；状态机 4 条迁移生效且非法迁移 400；单号 `PO-YYYYMMDD-NNNNNN` 连续不重；明细金额恒等被 CHECK 兜住 | 4 |
| **③** | **入库 + 库存 + 成本** | `V0032`；`stock_in/`、`inventory/` | 过账写出库存/流水/应付/凭证全套；**同物料同仓 20 并发过账结果与串行一致**；重复过账 400；超收被拒；一致性巡检 SQL 返回 0 行 | **7** |
| **④** | 应付 | `V0033`；`payable/` | 一入库单只生成一张应付（唯一键约束生效）；到期日=入库日+账期；核销金额校验；账龄分档正确 | 3 |
| **⑤** | **凭证引擎 + 总账** | `V0034`/`V0035`；`voucher/{model,engine}.rs`、`ledger/` | 规则命中/优先级/无规则拒绝三场景；四级科目解析链每条路径有单测；借贷平衡 L1/L2/L3 三层校验生效；红字冲销且原凭证 `REVERSED`；跨期冲销正确；试算平衡 `balanced=true`；规则 preview 与真实过账一致 | **9** |
| **⑥** | 前端 17 页 | `api/business/erp/*`、`views/business/erp/*`、`router` 追加、`utils/decimal.ts` | 全部页面可用且权限码一致；明细行金额自动算、含税切换不漂移；金额千分位/右对齐/负数红；`pnpm typecheck` 零错误；过账/作废二次确认展示影响面 | 13 |

**关键路径**：③ 与 ⑤ 是技术风险集中区，且 ⑤ 依赖 ③ 的数据流，**不能并行**。⑥ 中「采购订单」「入库」两页依赖 ②③，其余可提前用 mock 开发。

## 七、核心技术决策速查

| 决策 | 结论 |
|---|---|
| 金额类型 | Rust：`rust_decimal::Decimal`（`alun::prelude::rust_decimal`，无需额外声明依赖） |
| 金额/单价/余额 DB 类型 | `NUMERIC(18,4)` / `NUMERIC(18,6)` / `NUMERIC(20,4)` —— **单价必须比金额多 2 位**，否则移动加权累积误差 |
| 单据状态列 | `VARCHAR(24)` + `CHECK`（**故意偏离**底座 SMALLINT 约定，理由：会计/审计需直接读 SQL） |
| 凭证生成时机 | **入库即生成**，贷方记「应付账款—暂估应付款」（符合中国实务，为批次 2 发票冲回留路径） |
| 科目映射 | 规则模板「科目槽位」+ **四级解析链**（单据行 → 主数据 → 规则匹配 → 系统参数） |
| 库存并发 | `SELECT ... FOR UPDATE` 悲观行锁 + **按 material_id 升序加锁**（防死锁） |
| 成本法 | 移动加权平均；负数库存默认禁止（仓库级开关 `allow_negative`） |
| 单据取号 | PG 单语句原子 `UPDATE ... RETURNING`（不用 Redis） |
| 操作日志 | **双写**：`operation_logs`（中间件自动）+ `biz_doc_log`（事务内） |
| 迁移号段 | V0030–V0039（system 已到 V0022、business 已到 V0020，无冲突） |

⚠️ **`biz_doc_log` 存在的真实原因**：现有日志中间件 `describe_operation` 硬编码在 `src/middleware/`（红线禁改），且它是**异步旁路**——事务回滚后仍会落一条"过账成功"的假日志。所以业务操作轨迹必须在事务内自己写。

## 八、设计勘误（重要，开发前必读）

| 项 | 原设计（架构文档） | 实际情况 | 处理 |
|---|---|---|---|
| **D9 配色** | 「现有主色是 `#0580a2`，莫兰迪四色在代码里不存在，故不改 theme.less、莫兰迪降级为语义色」 | **该结论基于旧参考仓库 `cailu-src`，与实况不符。** `/opt/cailu/frontend/src/style/theme.less` 主色已是 `#51697C`（深海蓝），莫兰迪四色全站生效（commit `04792dc`） | **ERP 新页面直接沿用现有莫兰迪主题**，不需要"降级"。architect 提出的「莫兰迪色适合表达借贷方向/单据状态」作为**语义色补充**保留 |
| 权限码段数 | 任务书要求 `business:erp:material:*` 四段，底座约定三段 | 权限校验是 `SELECT DISTINCT auth_code` 的**字符串集合匹配**（无格式校验），四段可用 | ✅ 按四段执行 |
| 迁移号段 | 从 V0030 起 | system 最大 V0022、business 最大 V0020 | ✅ 无冲突，占 V0030–V0039 |

## 九、主要风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 凭证借贷不平（尾差/取数口径不一致） | **致命**（错账） | 贷方取单据级 `total_with_tax`；税额由"价税合计 − 不含税"倒挤不做二次乘法；DB `ck_biz_voucher_balance` 强制；引擎 L1 + 余额表 L3 双层校验；**过账失败优于错误入账** |
| R2 | 移动加权成本并发错误 | 成本失真 | 行锁 + 升序加锁；**20 并发测试**作为 ③ 的硬验收 |
| R3 | 与 alun 框架集成（无 service 层、错误三出口、宏路径） | 返工 | 架构文档 §3.0 已定模块结构，遵守项目 4 条硬红线 |
| R4 | 范围蔓延（顺手做销售/生产） | 延期 | 本文第三章"明确不做"清单为硬边界 |

## 十、如何启动开发

1. **确认排期方案**（A 单线 8.2 周 / B 并行 6 周）
2. 按本文第四章拆成 kanban 任务卡（每步一张，assignee 按 A/B 方案定）
3. 第一步（主数据+科目，5 人日）先行，完成后前端可并行
4. 每步完成必须过第六章里程碑检查点
5. 每步的验收由 laoliu 复核后进入下一步
