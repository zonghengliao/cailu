# 双版本说明（云枢版 / 原名版）

> 本文档在两版仓库里内容**完全相同**（`rename.sh` 对 `docs/双版本说明.md` 整文件跳过），
> 用来解释两个版本的关系、同步方式与红线。它本身是「中性文档」，不随改名脚本变化。

## 1. 两个版本是什么

| | 版本 A：云枢版（改名版） | 版本 B：原名版（未改名） |
|---|---|---|
| 项目标识 | `cloudpivot` / `CloudPivot` / 云枢 | `cailu` / `Cailu` / 菜芦 |
| Rust crate / 二进制 | `cloudpivot` | `cailu` |
| 前端包名 | `@cloudpivot/web` | `@cailu/web` |
| 用途 | **生产部署**（`/opt/cloudpivot`，systemd `cloudpivot.service`） | **向上游贡献 / 保留原名形态**（fork `zonghengliao/cailu`） |
| 部署态 | 是（目录/服务/数据库都按 cloudpivot 命名） | 否（只存在于代码仓库，不部署） |

**两版功能完全对等，唯一差异是命名。** 配色切换（8 套 × 明暗）、安全整改、状态卡、
ERP 模块、大数据设计文档、迁移包等全部一致 —— 因为它们是同一份代码经
`migration-kit/01-rename/rename.sh` 的两个方向互相推导出来的。

## 2. 命名映射（严格互逆）

| 正向（cailu → cloudpivot） | 反向（cloudpivot → cailu） |
|---|---|
| `cailu` → `cloudpivot` | `cloudpivot` → `cailu` |
| `Cailu` → `CloudPivot` | `CloudPivot` → `Cailu` |
| `菜芦` → `云枢` | `云枢` → `菜芦` |
| `cailu-setting`（localStorage 键） | `cloudpivot-setting` |
| `/opt/cailu`、`cailu.service`、库名 `cailu` | `/opt/cloudpivot`、`cloudpivot.service`、库名 `cloudpivot` |

**刻意不改的名字**（两个方向都原样保留，见 `migration-kit/01-rename/special-cases.md`）：

- `.gitleaks.toml` 规则 3 里**故意保留**的旧前缀 `cailu`：git 历史里已泄露的 JWT 字面量形态是
  `cailu-<env>-jwt-secret-*`，改名会让历史泄露从扫描器里消失（安全回归）。云枢版里这条规则同时匹配
  新旧前缀；原名版里它就是纯 `cailu` 形态。
- 外部上游仓库 URL/slug（`github.com/wild1024/cailu`）：那是别人的地址。
- `cailu-src`：另一台机器上的同技术栈参考工程目录名，不是本仓库。
- 少量**历史基线引用**（旧 crate 名、旧库名）：见 `special-cases.md` 特例 7 的 sticky 表。

## 3. 怎么从一版同步到另一版

一律用脚本，**禁止手改**（手改必然产生漂移，而漂移只有跑一遍往返校验才会暴露）。

```bash
# A) 云枢版 → 原名版（cailu）
cd /path/to/cailu-version
bash migration-kit/01-rename/rename.sh --reverse --dry-run   # 先看要改什么
bash migration-kit/01-rename/rename.sh --reverse             # 落盘（默认备份到 .rename-backup/）

# B) 原名版 → 云枢版（cloudpivot）
cd /path/to/cloudpivot
bash migration-kit/01-rename/rename.sh --dry-run
bash migration-kit/01-rename/rename.sh

# C) 自检（两个方向都有）
bash migration-kit/01-rename/verify.sh            # 云枢版：残留只允许 gitleaks + sticky
bash migration-kit/01-rename/verify.sh --reverse  # 原名版：cloudpivot/云枢 残留必须为 0

# D) 往返一致性（核心验收：反向+正向必须逐字节还原）
bash migration-kit/01-rename/verify-roundtrip.sh --base /opt/cloudpivot
bash migration-kit/01-rename/verify-roundtrip.sh --base /path/to/cailu-version --cailu-base
```

脚本特性：**幂等**（跑第二遍 0 改动）、**dry-run**（先看不落盘）、**默认备份**、**排除**
`node_modules/target/dist/.git/migration-kit`、**文件名与内容都改**、**自动重排 Cargo.lock 包块序**
（crate 改名后 lock 里的块位置要跟着字母序走，否则 cargo 下次构建会重写 lock）。

## 4. 改动流程（避免漂移）

1. **只在一个版本上改**（推荐在云枢版上改 —— 生产在跑，改完能立刻验证）。
2. 提交。
3. 用 `rename.sh`（对应方向）同步出另一个版本，单独提交。
4. 跑 `verify-roundtrip.sh`，`diff -r` 必须无差异。有差异 = 出现了「命名之外」的漂移
   （或者映射表漏了某个特例），**先修映射表再同步**，不要手改产物。
5. 两版的 `migration-kit/` 保持内容一致（它是工具，两个方向共用一份）。

> 反面案例：曾经在两版上各改各的（一边改配色、一边改文档），结果两版在
> `scripts/patch-alun-web.sh` 上出现「判重逻辑不同」的隐性差异，编译行为不一致。
> 这正是本流程要防的事。

## 5. 系统层不随代码命名切换

数据库、systemd 服务、`/opt` 目录、`/etc/*.env`、nginx 站点、bare 仓库这些属于**部署态**，
只有云枢版有（本机实际部署）。原名版**只存在于代码仓库**：

- 原名版的配置里写的是 `cailu` 库名/路径，**不要拿去部署**（本机没有 `cailu` 库与 `cailu.service`）；
- 想让原名版跑起来，需要另外按 `migration-kit` 的 02~05 步骤建一套独立环境；
- 反过来，把云枢版的代码 rsync 到部署机时，注意 `backend/config/*.toml` 里的库名/env 路径要与
  系统层一致（阶段 2 已对齐，不要再改）。
