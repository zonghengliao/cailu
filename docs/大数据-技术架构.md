### 0.1 二十五条硬结论

| # | 决策点 | 结论 | 一句话理由 |
|---|--------|------|-----------|
| **D1** | 菜芦与大数据平台的边界 | **大数据平台独立部署、独立运维；菜芦只做"控制面 + 服务面"**（数据集目录、仪表盘、MDM、权限、审计），**不管理 Flink/Kafka/Doris 集群生命周期** | Rust 进程去托 Java 集群生命周期的结果一定是"半个 K8s"，成本远超收益 |
| **D2** | 菜芦怎么读 Doris | **MySQL 协议**（FE `query_port=9030`），在 `business/bi` 内建**独立连接池**，用 alun 公开 API `Db::connect_with(url, DatabaseConfig)`，**不污染全局 `db()`** | 已核实 alun 0.4.2 的 `Db::connect_with` 是 pub API（见 §1.4）；全局池 `max_connections=10` 是业务 API 的生命线，绝不能被大查询占用 |
| **D3** | 大数据组件版本 | **JDK 17 单一运行时**：Kafka 4.3.1 + Flink 2.2.1 + flink-doris-connector 26.2.0 + Doris 4.0.8（+ Debezium 3.7.0） | Doris 3.0+/Flink 2.x/Kafka 4.x 都要求 JDK 17，统一后只需维护一个 JDK；connector 26.2.0 官方矩阵最高支持 Flink **2.2**，故 Flink 不上 2.3 |
| **D4** | 部署形态 | 第 1 批**单机（方案 A，32C/128G/4T）**跑全栈，**同一套部署脚本**可平移三节点（方案 B） | 第 1 批数据量 4 GB 级（§5.7 实测容量账），单机足够；先拿闭环，再谈横向扩展 |
| **D5** | CDC 部署形态 | **Debezium Server（单 JVM 进程，`debezium.sink.type=kafka`）**，不部署 Kafka Connect 集群 | Connect 集群要额外运维 REST/offset/status 三类主题与 worker 再平衡；我们只有 1~N 个连接器，Server 模式省一个分布式系统 |
| **D6** | 消息格式 | 第 1 批**JSON + `schemas.enable=false`**，主题名带 `v1`；**第 2 批（表数 ≥5 或首次 schema 变更）再上 Apicurio Registry + Avro** | Debezium 内联 schema 的 JSON 单条 1~3 KB（实测 pgoutput 裸事件只有 **395 B**），第 1 批上 SR 的收益未兑现，成本是一个常驻服务 + 两侧 converter 配置 |
| **D7** | 复制槽 WAL 堆积防护 | **`max_slot_wal_keep_size=4GB`（PG 侧硬保险）+ `heartbeat.action.query=pg_logical_emit_message` + 发布只含目标表 + 磁盘水位三级告警 + 看板常驻 `retained_wal` 曲线** | PG 默认 `max_slot_wal_keep_size=-1`（**无限保留**，本机实测确认）；实测未消费槽 474~496 MB → checkpoint 后被判 `lost`。宁让 CDC 断（重新快照），不让业务库盘满宕机 |
| **D8** | 快照与增量衔接 | `snapshot.mode=initial` + 逻辑槽创建时的一致性快照 + 增量快照信号表（`debezium_signal`）做重灌；**禁止 `slot.drop.on.stop=true`** | 槽一旦丢失，唯一安全路径是"丢槽 + 全量重灌"；实测丢失后访问槽报 `invalidated due to "wal_removed"` |
| **D9** | `REPLICA IDENTITY` | 只有"无主键表 / 需要完整 before-image 的表"设 `FULL`；主键表保持默认 | 实测 `FULL` 让 UPDATE 的 WAL 从 758~876 B/行涨到 962~1,445 B/行（**+27%~+65%**），全表开等于给业务库凭空加 1/4 到 2/3 的 WAL |
| **D10** | Exactly-Once | **分层两策略**：ODS 明细入仓用 **Doris Stream Load 2PC（connector 默认 `sink.enable-2pc=true`）**；DWS 聚合用 **幂等覆盖写（Unique Key + 窗口全量重算）** | 明细行必须"精确一次"防重复计钱；聚合结果天然幂等，用 2PC 反而把 checkpoint 周期和可见性耦死，还会放大长事务风险 |
| **D11** | Checkpoint | 间隔 **30 s**、`unaligned-checkpoints` 开启、状态后端用默认堆内（作业无大 keyed state）、checkpoint/savepoint 落地到大数据机本地目录 + 每日 rsync 到备份盘 | 30 s 决定大屏端到端延迟上界；管道型作业状态只有 Kafka offset，几百 KB 级，不需要 RocksDB |
| **D12** | OLAP 选型 | **Apache Doris 4.0.8**（3.1.4 作为回退版本）；不用 ClickHouse、不用 StarRocks | 见 §5.1 对比表：本场景要"高频 upsert + 多表 join + 高并发点查 + 低运维 + 中文生态"，Doris 是唯一五项都不掉分的 |
| **D13** | Doris 数据模型 | ODS：**Unique Key(MoW)**；DWD：**Unique Key(MoW) + 部分列更新**；DWS：**Unique Key（预聚合结果按维度覆盖）**；ADS：**Unique Key 或 Aggregate（SUM/REPLACE）**；日志类：**Duplicate** | 逐场景给理由见 §5.3；一句话：**分析结果要能被"改"，就必须有主键** |
| **D14** | 分区分桶 | 按天 `PARTITION BY RANGE(dt)` + 开启动态分区（热 90 天/冷归档）；bucket 按"单分区 ≤ 1~2 GB"反推，第 1 批 ODS 日分区 **8 桶**、DWS 维表 **1~4 桶** | 亿级下分区裁剪比任何索引都重要；桶太多小文件拖慢导入，桶太少单 tablet 太大影响并行度 |
| **D15** | 物化视图 | 第 1 批只上 **1 个异步物化视图**：`ads` 层"部门×月×供应商"采购金额汇总 | 大屏 90% 请求打在同一口径上；先验证 MV 的透明改写与刷新成本，再批量铺 |
| **D16** | 数据湖 | **第 1 批不上 MinIO + Paimon/Iceberg**，Doris 即唯一事实存储 | 见 §6.1 的 4 条量化理由与 3 个触发条件；上了湖，第 1 批就要多养一套对象存储 + 元数据 + 表格式三件套 |
| **D17** | BI 查询安全 | **标识符来自白名单（`bi_dataset_field.column_name`），值一律参数绑定**；SQL 由服务端模板拼装，前端**永不提交 SQL 片段** | SQL 注入在自研 BI 里等于"任意读全库"；白名单 + 绑定参数是唯一能同时保证安全与可维护的做法 |
| **D18** | 行级数据权限 | **查询改写**：把权限范围解析成 `dept_id IN (?,?,…)` 注入 WHERE，权限集在 Redis 缓存（TTL 300 s）；**不用 Doris 视图、不用 Doris Row Policy** | 视图数量 = 角色×数据集组合爆炸；Row Policy 需要把菜芦角色同步成 Doris 角色，且 `root/admin` 免疫策略（实测文档口径），漏一个就是数据泄漏 |
| **D19** | 列级脱敏 | **改写时把字段表达式换成脱敏函数 + 结果集二次脱敏**（双保险），脱敏策略存 `bi_column_mask` | 只做 SQL 层脱敏，分析师可以在 SQL 工作台用 `concat`/子串绕过；结果集再过一遍才闭环 |
| **D20** | 结果缓存 | **Redis**，键 = `sha256(dataset + 规范化 SQL + 行权限签名 + 数据集版本)`，TTL 分级（大屏 60 s / 固定报表 300 s / 自助取数 0~60 s），`bi_query_log.sql_fingerprint` 与缓存键同源 | 秒级大屏的"秒级"应该来自缓存 + 预聚合，不是每次都硬扫 Doris |
| **D21** | 分析师 SQL 工作台 | 只读账号 + 库表白名单 + 强制 `LIMIT` + 语句超时 + Doris workload group 并发/排队 + 结果行数上限 + 全量审计；**禁止 DDL/DML/`LOAD`/`EXPORT`/`SELECT INTO OUTFILE`** | 自助取数与分析师 SQL 是同一套引擎里的两种"特权"，必须用资源组隔离，否则一个笛卡尔积拖垮当天所有报表 |
| **D22** | MDM 属性建模 | **关键列下沉 + 其余属性 JSONB**（`mdm_record.record_code/record_name` 为列，`attrs` 为 JSONB + GIN 索引） | 纯 EAV 查询要 5 表 join 且无法建唯一索引；纯宽表不能支撑"任意主数据域"。混合方案是本场景唯一解 |
| **D23** | MDM 合并/拆分 | 合并保留**权威记录 + 编码别名表**；`merge_log.snapshot` 存合并前全量快照支撑 unmerge；**编码一旦使用不释放**（`uk_mdm_rec_code` 不含 `is_merged` 条件） | 这是本设计在真库验证中**发现并修正的一个真实缺陷**：早期版本"合并后释放编码"会让 unmerge 与新记录撞唯一键（§1.7 复现记录） |
| **D24** | MDM 与 ERP 的关系 | **MDM 是主数据权威源，ERP 订阅**（Kafka 事件 + 拉取兜底）；ERP 本地只读副本 + 允许本地扩展字段，**不允许 ERP 自建物料编码** | 编码唯一性/去重/跨系统一致性只有在单一权威源下才成立；ERP 自管 + MDM 汇总 = 两套编码，第 2 批必然返工 |
| **D25** | 血缘采集方式 | 第 1 批做**表级 + 登记式**（Flink SQL 文件头注释 → CI 生成 `lineage.yaml`），**不解析 SQL**；字段级与 SQL 解析留第 2 批 | 解析 Flink SQL 方言 + 自定义 connector 的准确率撑不住"改表前查谁在用"这个用途；登记式的准确率是 100%，代价只是规范约束 |

### 1.3 实验 1：一行变更到底产生多少 WAL【实测】

表结构对齐 ERP `biz_material`（18 列 + 4 索引）与单据行（20 列 + 3 索引），`wal_level=logical`。

| 场景 | 行数 | WAL 字节（第 1 次 / 第 2 次独立运行） | 每行字节 |
|---|---|---|---|
| 主数据 INSERT | 200,000 | 136,862,584 / 136,879,784 | **684 B/行**（两次一致） |
| 主数据 UPDATE（`REPLICA IDENTITY DEFAULT`） | 200,000 | 151,638,384 / 175,301,808 | **758 ~ 876 B/行** |
| 主数据 UPDATE（`REPLICA IDENTITY FULL`） | 200,000 | 192,504,456 / 288,963,984 | **962 ~ 1,445 B/行**（比默认 **+27% ~ +65%**） |
| 单据行 INSERT | 500,000 | 313,596,464 / 338,397,184 | **627 ~ 677 B/行** |
| 单据行 单行 UPDATE | 1 | 8,832 / 8,832 | **8.8 KB/次**（固定开销 ~8 KB，与行宽无关） |

> **为什么同一脚本跑两遍数字不一样**：差异来自 `full_page_writes`（checkpoint 之后第一次改某个页面时会写整页 8 KB 镜像）。所以"每行 WAL"不是一个常数，而是**区间**；做容量规划取区间上界。这也是为什么 §3.5 的防护要用"4 GB 硬上限 + 告警"，而不是算准一个数。

**直接推论**（写入 §3.2 与 §5.7）：

1. **一次单行 UPDATE 的 WAL 成本 ≈ 8.8 KB**，与行宽无关 —— "高频小事务"比"批处理大事务"贵 10 倍以上。菜芦侧应尽量合并写（ERP 批次已做批量凭证，BI/MDM 侧不要再拆成一条条 UPDATE）。
2. 亿级数据落实：日增 500 万行明细 + 1.5 倍更新 → **WAL ≈ 9.2 ~ 10.2 GB/日**（§5.7 计算，取 10 GB 做规划），月 280~305 GB。**只要不堆积，4T 盘毫无压力；一旦槽卡住，10 GB/日意味着 4T 盘约 400 天写满 —— 但生产环境一定是先被 85%/95% 告警拦下，所以真正的风险是"没人看告警"，不是"盘不够"**（§3.5 给出可执行的三级告警）。
3. `REPLICA IDENTITY FULL` 是**付费功能**：多 27%~65% 的 WAL 换完整 before-image，只给"无主键表"或"审计必须要旧值"的表开。

### 1.4 实验 2：逻辑解码（pgoutput）的真实事件体积【实测】

发布 `pub_probe` + 槽 `slot_decode`，产生 20,000 INSERT + 5,000 UPDATE：

| 指标 | 值 |
|---|---|
| 解码消息数 | 25,005（含 Begin/Commit 边界） |
| 解码总字节 | 9,879,881 B |
| **平均每条消息** | **395.1 B** |
| DML 消息（>100 B）均值 | **395.2 B** |

对照：同一行 `row_to_json` 纯数据 **563 B**，Debezium JSON 若 `schemas.enable=true` 会在每条消息里内联 schema（同类表通常 1~3 KB/条）。

**结论**：D6 的"第 1 批用 `schemas.enable=false` JSON"是有量化依据的 —— 消息体膨胀 3~8 倍，直接把 Kafka 带宽、Flink 反序列化 CPU、磁盘保留全部乘上去，而第 1 批只有 1 张表、schema 稳定，收益为零。

### 1.5 实验 3：复制槽未消费 → WAL 堆积 → 槽失效（真实事故链路复现）【实测】

`max_slot_wal_keep_size='512MB'`（`ALTER SYSTEM` + reload），槽 `slot_decode` 无消费者，然后写入 400,000 行填充数据制造 WAL：

| 阶段 | 槽状态 | `retained_wal` | `safe_wal_size` |
|---|---|---|---|
| 造数后 | `active=f`，`wal_status=**unreserved**` | **474 MB** | **-220,840,232 B（负值 = 已超限）** |
| `CHECKPOINT` 后 | `active=f`，`wal_status=**lost**` | —（槽已被判失效） | — |
| 尝试使用该槽 | `ERROR: can no longer access replication slot "slot_decode"`<br>`DETAIL: This replication slot has been invalidated due to "wal_removed".` | | |

**这是本文档最重要的一条实况**：

- PG **默认 `max_slot_wal_keep_size=-1`（无限）**，此时槽会持续 pin 住 WAL 直到磁盘写满 → PG 写入 `WAL` 失败 → 数据库 **PANIC / 只读 / 宕机**。这不是理论：任务书点名的"真实生产事故"就是它。
- 设了上限之后，PG 的行为是**牺牲 CDC、保业务库**：槽被标记 `lost`，Debezium 恢复时报 `invalidated due to "wal_removed"`，**唯一恢复路径是丢槽 + 全量重灌**（Debezium 的 snapshot 机制 + 我们的重灌 SOP）。
- 因此 §3.2 的防护是"**多道闸门**"，不能只靠一个参数。

### 1.6 实验 4：行级数据权限三种写法的真实耗时【实测】

1,000,000 行 `dws_purchase_dept_day`（部门×日×供应商），取 1 个事业部 + 20 个子部门（21 个 `dept_id`），查 90 天汇总：

| 写法 | 计划要点 | 执行时间 | 说明 |
|---|---|---|---|
| A. 改写为 `dept_id IN (值列表)` | Bitmap 扫全时间段 9 万行 + Hash Join | **17.18 ms** | 大 `IN` 列表没带来裁剪收益 |
| A3. `dept_id IN (子查询 sys_dept WHERE dept_path LIKE …)` | Hash Join | **13.67 ms** | 同上 |
| **B. 子查询 + `dept_path` 前缀，按部门逐个 Nested Loop** | 21 次索引定位（`(dept_id, stat_date)` 主键） | **2.33 ms** | **最快，7.4×** |
| C. 无行级过滤（对照组） | 扫 9 万行 | 16.98 ms | 权限过滤本身几乎免费 |

**结论**（写进 §7.4）：

1. 行级权限**不是性能瓶颈**（21 部门 vs 全量：耗时同一量级）——所以不必为它设计 Doris 视图或复杂预计算。
2. 但"权限集大小 × 扫描方式"决定成败：**部门子树必须能一次解析成 `dept_id` 集合**（`dept_path` 前缀是最省的做法），且集合应有上限（本设计取 **≤500 个 dept_id**，超过则退化为"按权限维度表 join"）。
3. Doris 侧没有 B-tree，靠**分区裁剪 + 前缀索引**；因此改写规则里必须**永远带上时间分区条件**，不能只靠 `dept_id IN`。

### 1.7 实验 5：BI + MDM 的 20 张表在真库验证【实测】

- `bi_mdm_ddl.sql` 在 PG 18.6 执行：**20 张表，0 个错误**（`grep -c ERROR` = 0）。
- 6 组"必须被拦住"的负向用例全部按设计拦住：

| 负向用例 | 拦截者 | 结果 |
|---|---|---|
| 同域同编码重复插入 | `uk_mdm_rec_code` | ✅ `duplicate key value violates unique constraint` |
| 疑似重复对顺序颠倒（left > right） | `ck_mdm_dup_order` | ✅ check constraint 拒绝 |
| measure 字段缺聚合函数 | `ck_bi_field_role_agg` | ✅ check constraint 拒绝 |
| 同一数据集重复映射同一物理列 | `uk_bi_field_column` | ✅ unique 拒绝 |
| 行级范围 `DEPT_AND_CHILD` 却缺 `dept_id` | `ck_bi_scope_dept` | ✅ check constraint 拒绝 |
| 合并后被合并方编码再次使用 | `uk_mdm_rec_code` | ✅ 拒绝（设计如此，见下） |

- **过程中发现并修正 1 个真实设计缺陷**（关键收获）：

  > 初版把唯一索引写成 `... WHERE deleted_at IS NULL AND is_merged = FALSE`，意图是"被合并方释放编码"。真库跑 `unmerge` 时复现失败：`duplicate key value violates unique constraint "uk_mdm_rec_code"` —— 因为 unmerge 把被合并方恢复成活跃记录时，同编码已被新记录占用。
  >
  > **修正**：唯一索引去掉 `is_merged` 条件（编码**一旦使用即不释放**，删除只走 `deleted_at` 软删）。修正后 `unmerge` 顺利恢复为 `status=PUBLISHED, is_merged=f`。这条写进 §8.4 的"合并语义三条铁律"。

### 1.8 实验 6：MDM 编码取号并发安全【实测】

`pgbench -c 8 -j 4 -t 60`（8 并发 × 60 事务），每条事务执行单语句 `UPDATE mdm_code_rule SET current_seq=current_seq+1 ... RETURNING 编码` 并插入 `seq_probe(code UNIQUE)`：

```
number of transactions actually processed: 480/480
number of failed transactions: 0 (0.000%)
latency average = 1.912 ms
tps = 4183.95
total|distinct_codes|min|max  →  480|480|M202610000002|M202610000481
```

**结论**：**单语句 `UPDATE ... RETURNING` 取号在 480 并发事务下 0 重号、0 失败、4.2k TPS**，不需要 Redis 分布式锁，也不需要序列应用层重试。菜芦 ERP 批次 D10 的同类结论在 MDM 上复现成立。

### 2.2 菜芦 vs 大数据平台：职责矩阵（谁负责什么，写死在纸上）

| 能力 | 菜芦（Rust） | 大数据平台（Java/JVM + Doris） | 说明 |
|---|---|---|---|
| 用户/角色/部门/菜单/权限码 | ✅ 唯一负责 | ❌ | `sys_user`/`sys_role`/`sys_dept`/`sys_menu.auth_code` 是权威源 |
| 数据集/指标/仪表盘/图表配置 | ✅ 唯一负责 | ❌ | 配置元数据存菜芦 PG（§7.2 表设计） |
| 查询编排、SQL 生成、结果缓存 | ✅ 唯一负责 | ❌ | 菜芦生成 Doris SQL 并执行 |
| 行级/列级数据权限判定 | ✅ 判定与改写 | ❌（不使用 Doris Row Policy） | 见 D18/D19 |
| MDM 域建模、去重、合并、审核、发布 | ✅ 唯一负责 | ❌ | 菜芦 PG + Rust |
| 大数据侧元数据采集（表/字段/分区/数据量） | ✅ 展示与登记 | ✅ 产生（`information_schema`） | 菜芦定时拉取 |
| Doris/Kafka/Flink 进程与集群 | ❌ **绝不** | ✅ 脚本化部署与运维 | 菜芦不托管生命周期（D1） |
| Kafka topic 规划与保留策略 | ❌ | ✅ | 菜芦不建 topic |
| Flink 作业提交/升级/savepoint | ❌ | ✅（Git + 脚本） | 菜芦不调 Flink REST API |
| Doris 用户/角色/授权 | ❌ | ✅ | 菜芦账号**不映射**成 Doris 账号（见 §10.3） |
| 业务数据写入（PG） | ✅ 权威源 | ❌ 只读 | Debezium 只用只读复制账号 |
| 备份/恢复 | ✅ PG 备份 | ✅ Doris/Kafka/Flink 状态备份 | 两套各自负责 |

**边界原则一句话**：**菜芦管"人、口径、权限、配置"；大数据平台管"数据怎么流、怎么算、怎么存"。** 任何一边越界都是运维灾难。

### 2.3 通信协议清单（第一批实际用的 4 条）

| 方向 | 协议 | 端口 | 认证 | 连接池 / 并发上限 |
|---|---|---|---|---|
| 菜芦 → Doris（查询） | **MySQL 协议**（sqlx-mysql via alun `mysql` feature） | 9030 | Doris 用户 + 密码（TLS 可选） | 独立 `Db` 实例：`max_connections=20`、`min_connections=2`、`acquire_timeout=5s` |
| Flink → Doris（写入） | **Stream Load HTTP**（connector 内部） | 8030（FE HTTP） | Doris 用户 + 密码 | 每 sink 并行度 ≤ 8，批 5000 行 / 100 MB |
| Debezium → Kafka | Kafka 协议（幂等生产者，`acks=all`） | 9092 | SASL/PLAIN 或内网 + ACL | 单连接器 `tasks.max=1` |
| 菜芦 → Kafka | **不直连**（第一批） | — | — | MDM 分发用"菜芦 PG 表 → Debezium 捕获"的方式复用同一条管道（§8.6） |

**为什么查询选 MySQL 协议而不是 Doris HTTP API（`/api/query`）**

| 维度 | MySQL 协议（9030） | HTTP `/api/query`（8030） |
|---|---|---|
| 驱动/生态 | 任何 MySQL 驱动可用，`sqlx` 原生；类型映射成熟 | 需手写 JSON 编解码与类型转换 |
| 结果集类型 | 二进制协议，`NUMERIC/DATE` 精确 | JSON 数字精度需自行处理（金额会踩坑） |
| 连接池 | 标准池（`Db::connect_with` 直接复用） | 自建 HTTP 客户端池 + 会话管理 |
| 长查询/异步 | 受 `query_timeout` 控制 | 支持 `/api/query/{query_id}` 异步取结果（更灵活） |
| 权限 | Doris 用户/角色权限生效 | 同样生效 |
| **结论** | ✅ **主通道** | 仅用于"导出大结果集"与运维排障（`/api/query` 拿 `query_id` 再分页拉） |

**连接池怎么管**（关键实现约束，基于 alun 实测）：

```rust
// business/bi/query/pool.rs —— 独立 Doris 连接池，与全局 PG 池完全隔离
use alun::prelude::*;
use std::sync::OnceLock;

static DORIS: OnceLock<Db> = OnceLock::new();

pub async fn init_doris(cfg: &BiDorisConfig) -> Result<()> {
    // Db::connect_with 是 alun-db 的公开 API（0.4.2 已核实，$CARGO/registry/.../alun-db-0.4.2/src/db.rs:51）
    let db = Db::connect_with(
        &format!("mysql://{}@{}:{}/{}", cfg.user, cfg.host, cfg.port, cfg.database),
        DatabaseConfig {
            db_type: "mysql".into(),
            url: format!("mysql://{}@{}:{}/{}", cfg.user, cfg.host, cfg.port, cfg.database),
            password: cfg.password.clone(),
            pool: PoolConfig {
                max_connections: 20,       // ≠ 全局 PG 池的 10
                min_connections: 2,
                connect_timeout: std::time::Duration::from_secs(5),
                idle_timeout: Some(std::time::Duration::from_secs(300)),
                max_lifetime: Some(std::time::Duration::from_secs(1800)),
            },
        },
    ).await?;
    DORIS.set(db).ok();
    Ok(())
}

// 连接未初始化时必须显式失败，不做 panic/占位返回
pub fn doris() -> Result<&'static Db> {
    DORIS.get().ok_or_else(|| alun::Error::internal("Doris 连接池尚未初始化（检查 bi 模块启动顺序）"))
}
```

> **依赖铁律没破**：`mysql` 是 `alun` 的 feature（`alun-db-driver-mysql` 是它的可选依赖），`Cargo.toml` 仍然只声明 `alun` 一个框架 crate —— 写法是 `alun = { features = ["db","postgres","mysql","cache", ...] }`。
> **风险与后路**：Doris FE 只保证兼容 MySQL 5.7+ 客户端；`sqlx-mysql` 的握手/类型映射必须在 §11 第 ④ 步做 POC。若不通，后路是"BI 查询服务独立成 workspace 成员 `bi-service`，直接用 `mysql_async`"，菜芦主 API 通过内网 HTTP 调它 —— 架构不变，只换实现载体。

> 表名沿用 ERP 批次设计（`cailu-erp-batch1-architecture.md` §2）。若 ERP 尚未建表，第 1 批用 `biz_purchase_order*` 的"最小可用子集"（`id, order_no, supplier_id, dept_id, biz_date, status, total_amount` + 行的 `material_id, qty, price, amount`）先打通，字段后续补齐走 schema 变更流程（§3.6）。

### 3.3 发布（publication）与槽（slot）命名规范

```sql

```

| 对象 | 命名 | 示例 | 约束 |
|---|---|---|---|
| 发布 | `dbz_<库简称>` | `dbz_cailu` | **每个连接器独享一个发布**（共享发布会互相抢事件且无告警） |

> 坑（文档口径）：多个 connector 共用一个槽时，**每条变更只会投递给其中一个**，Postgres 不会报错。这是"数据莫名丢失"的经典成因，所以规范里写死"一连接器一槽一发布"。

### 3.5 WAL 堆积防护：四道闸门（对应任务书点名的真实事故）

| # | 闸门 | 位置 | 触发值 | 动作 | 谁做 |
|---|---|---|---|---|---|
| 1 | **`max_slot_wal_keep_size=4GB`** | PG 参数 | WAL 保留 > 4 GB | PG 判定槽 `lost`（实测行为，§1.5），**业务库写入不受影响** | DBA/部署脚本 |
| 2 | **心跳** | Debezium | 每 10 s 一次 `pg_logical_emit_message` | 即使目标表无写入，槽位也前进（`confirmed_flush_lsn` 推进） | 连接器配置 |
| 3 | **发布范围最小化** | 建表规范 | 只发布 3 张表 | 其他表的 WAL 不进槽的解码范围（`restart_lsn` 仍 pin，但 `max_slot_wal_keep_size` 兜底） | 开发 |
| 4 | **磁盘水位三级告警** | 监控 | 70% / 85% / 95% | 70% 通知、85% 自动扩 `max_slot_wal_keep_size` 前先查槽、95% 触发"停 CDC 保业务库"预案 | 运维 |

**常驻监控 SQL（贴到 Doris 看板/菜芦 `business/monitor`）**

```sql
-- 槽保留量 + 状态（每分钟采一次，>2GB 或 wal_status != 'reserved' 即告警）
SELECT slot_name,
       active,
       wal_status,                                                   -- reserved / extended / unreserved / lost
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS unconfirmed_lag,
       confirmed_flush_lsn
FROM pg_replication_slots
WHERE slot_type = 'logical';

-- 解码统计（spill 高说明事务太大，需要调大 logical_decoding_work_mem）
SELECT slot_name, spill_txns, spill_count, spill_bytes, total_txns, total_bytes
FROM pg_stat_replication_slots;

-- 磁盘水位（95% 预案的判据）
SELECT pg_size_pretty(pg_database_size(current_database())) AS db_size;
```

> 补充：`logical_decoding_work_mem`（默认 64 MB）要在目标库调到 `256MB` —— 大批量 UPDATE（月结、批量改价）会产生超大事务，解码溢出到磁盘会拖慢整个槽的推进速度。

### 3.6 消息格式与 Schema Registry（D6 的完整论证）

| 方案 | 单条体积 | 生态 | 变更影响 | 运维成本 | 第 1 批推荐 |
|---|---|---|---|---|---|
| **JSON + `schemas.enable=true`（Debezium 默认）** | ~1~3 KB（内联 schema） | 无依赖 | 下游要处理 schema 字段 | 0 | ❌ |
| **JSON + `schemas.enable=false`** | **~400~600 B**（实测 pgoutput 395 B，JSON 冗余后约 1.3×） | 无依赖 | 加字段=下游忽略；删/改字段=下游报错（需人工对齐） | 0 | ✅ **第 1 批** |
| Avro + Apicurio Registry（Apache 2.0） | ~250~450 B（二进制 + schema id） | Flink/Apicurio converter 成熟 | 兼容性规则自动校验（BACKWARD 默认） | 1 个常驻服务 + 两侧配置 | 第 2 批 |
| Avro + Confluent Schema Registry | 同上 | 生态最好 | 同上 | **Confluent Community License（非 Apache 2.0）**，商用需评估许可 | ❌ 不接受 |

**切换触发条件（写死在文档里，避免"以后再说"变成永远不做）**：满足任一即上 Apicurio —— ① CDC 表数 ≥ 5；② 发生第一次"下游因字段变更失败"；③ 出现第 2 个消费方（如 ERP 订阅 MDM）。

**Apicurio 而不是 Confluent 的理由**：Apicurio 提供 Confluent 兼容 API（`/apis/ccompat/v7|v8`，官方文档声明 v7/v8 fully supported），客户端零改造即可迁移；许可为 Apache 2.0，规避 Confluent Community License 的商用限制。代价：`schema linking`/加密等高级特性不支持 —— 我们不需要。

### 3.7 全量初始化 + 增量衔接的一致性保证

Debezium 的初始快照本身就是**一致性快照**：PG 侧在同一事务里创建槽并导出快照，`snapshot` 事件携带 `snapshot=true` 标记，之后从槽的 `consistent_point` 开始流式。

**第一批落地顺序（必须按此顺序，否则会丢/重）：**

```
1. 建表 + 建发布（publication）
2. 建信号表 debezium_signal
3. 启动 Debezium Server → 自动 CREATE_REPLICATION_SLOT（pgoutput, EXPORT_SNAPSHOT）
4. 快照阶段：Debezium 读 3 张表的全量（读锁极短，snapshot.lock.timeout.ms=-1 不阻塞业务）
5. 快照完成 → 从 consistent_point 开始消费 WAL（期间业务写入不丢）
6. Flink ods_sync 作业：快照事件与增量事件走同一条 Upsert 路径（Doris Unique Key 天然幂等）
```

**唯一需要人工保证的**：`pt. 4` 期间**不要**对 3 张表做 `TRUNCATE`/`ALTER TABLE ... DROP COLUMN`（Debezium 对 DDL 的处理是"尽力而为"，删列会让 `after` 结构变化而下游 DDL 没跟上）。§3.6 的 schema 变更 SOP 管这件事。

### 3.8 重灌（resnapshot）SOP：槽失效后唯一正确路径

```
① 确认影响：SELECT slot_name, wal_status FROM pg_replication_slots;   -- lost
② 停 Flink 相关作业（savepoint 后可停）：
     flink stop -p hdfs:///... <jobId>  → 第一批用 -p file:///data/flink-savepoints/<jobId>
③ 删槽 + 重建发布（槽失效后无法复用，实测报 invalidated due to wal_removed）
     SELECT pg_drop_replication_slot('dbz_cailu_purchase');
     DROP PUBLICATION IF EXISTS dbz_cailu; CREATE PUBLICATION ...;
④ 清目标表当日分区（Doris）：ALTER TABLE ods_purchase_order_line DROP PARTITION p20261028;
⑤ 重启 Debezium Server（snapshot.mode=initial 会重新全量）
⑥ 验证三件套：Debezium 日志出现 "Snapshot completed"；Kafka topic 有 snapshot=true 事件；
   Doris 目标表 count(*) 与 PG 侧 count(*) 一致（用 §9.2 的唯一性/行数校验 SQL）
⑦ 启 Flink 作业（从 ④ 的 savepoint 恢复，若无则从最新 checkpoint 或空状态启）
```

> **能力上线要求**：这套 SOP 必须写成脚本 `/opt/bigdata/bin/cdc-resnapshot.sh <table>` 并在 §11 第 ② 步验收时**演练一次**（含"故意让槽失效"的故障注入）。写不出脚本的 SOP 等于没有。

### 3.9 PG 16 vs PG 18 的差异（本设计对两者的兼容性）

| 关注点 | PG 16 | PG 18.6 | 对本方案影响 |
|---|---|---|---|
| `wal_level=logical` | ✅ | ✅ | 无差异 |
| `pgoutput` 插件 | ✅ 内置 | ✅ 内置 | 无差异 |
| `pg_logical_emit_message`（心跳用） | ✅（13+） | ✅ | 无差异 |
| `max_slot_wal_keep_size` | ✅（13+） | ✅ | 无差异 |
| 逻辑解码内存控制 `logical_decoding_work_mem` | ✅ | ✅ | 无差异 |
| 增量快照（Debezium 侧实现，不依赖 PG 版本） | ✅ | ✅ | 无差异 |
| 仓库实际镜像 vs 本机版本 | `docker/init/Dockerfile` = `postgres:16-alpine` | 本机 18.6 | **部署时必须二选一并对齐**：若生产用 16，本设计的参数在 16 上同样成立；若升 18，需先做一次 ERP 数据迁移与回归（不在本批范围） |

**第二条灰度建议**：**先在 PG 从库上做 CDC 快照验证**（若未来有只读副本），避免初始快照的全表扫描压到主库 —— 第 1 批数据量小（3 张表百万级），可接受主库快照；第 2 批数据量上来后必须走"从库快照 + 主库增量"（Debezium 3.6+ 已支持在只读副本上做增量快照，文档口径）。

## 4. 实时计算（Flink）

### 4.1 作业拓扑：三个作业，职责单一

```
Kafka: cdc.public.biz_purchase_order_line
   │
   ├─[job 1: ods_sync]─► Doris: ods_purchase_order_line   (Unique Key, 全列镜像, 2PC 精确一次)
   │                       字段：id, after(JSON), op, ts_ms, dt(分区)
   │
   ├─[job 2: dwd_clean]─► Doris: dwd_purchase_order_line  (Unique Key, MoW, 清洗+维度补全)
   │                       清洗：金额空→0、负数量标记、supplier_id 补全（join dwd_supplier）
   │
   └─[job 3: dws_agg]───► Doris: dws_purchase_dept_day    (Unique Key, 分钟级滚动聚合)
                           维度：dept_id × stat_date × supplier_id
                           度量：order_cnt, amount_sum, amount_avg, last_update_ts
```

**为什么拆 3 个作业而不是 1 个 DAG**：

| 拆分 | 1 个作业 | 3 个作业（推荐） |
|---|---|---|
| 故障隔离 | 清洗逻辑 bug 会让入仓一起挂 | 只停 `dwd_clean`，ODS 照常入仓（数据不丢） |
| 恢复速度 | 状态大，恢复慢 | 每作业状态只有 offset + 少量聚合状态，秒级恢复 |
| 迭代节奏 | 改聚合 SQL 要重启整条链 | 只重启 `dws_agg` |
| 资源隔离 | 一个 TM 抢内存 | 可给 `dws_agg` 单独的 slot/内存 |
| 代价 | — | 3 倍 checkpoint 数量（但每个很小，可忽略） |

**第一批判定：用 3 个作业。** 理由不是"架构优雅"，而是"第 1 批一定会反复改清洗和聚合口径" —— 拆开每次只重启 30 秒的那个。

### 4.2 Flink SQL（作业即代码，进 Git）

`jobs/01_ods_sync.sql`：

```sql

CREATE TABLE cdc_purchase_line (
  `before` STRING,          -- Debezium JSON：{"before":...,"after":...,"op":...}

  'connector' = 'kafka',
  'topic' = 'cdc.public.biz_purchase_order_line_v1',
  'properties.bootstrap.servers' = '10.0.0.20:9092',

CREATE TABLE doris_ods_purchase_line (

  order_id    STRING,
  material_id STRING,
  dept_id     STRING,
  supplier_id STRING,
  qty         DECIMAL(18,4),
  price       DECIMAL(18,6),
  amount      DECIMAL(20,4),
  biz_date    DATE,

  JSON_VALUE(`after`, '$.id')            AS id,
  JSON_VALUE(`after`, '$.order_id')      AS order_id,
```

`jobs/03_dws_agg.sql`（分钟级滚动聚合，幂等覆盖）：

```sql
-- 用事件时间 + 1 分钟滚动窗口，保证"同一分钟重复计算"的结果幂等（Unique Key 覆盖）
INSERT INTO doris_dws_purchase_dept_day
SELECT
  dept_id,
  CAST(TO_DATE(FROM_UNIXTIME(window_start / 1000)) AS DATE) AS stat_date,
  supplier_id,
  COUNT(*)               AS order_cnt,
  SUM(amount)            AS amount_sum,
  AVG(amount)            AS amount_avg,
  MAX(ts_ms)             AS last_update_ts
FROM TABLE(TUMBLE(TABLE cdc_purchase_line_typed, DESCRIPTOR(event_time), INTERVAL '1' MINUTE))
WHERE op <> 'd'
GROUP BY dept_id, supplier_id, window_start, window_end;
```

> **注意：第 1 批 `dws_agg` 用"日粒度覆盖 + 分钟级增量修正"两条流**（日粒度读 DWD 重算当日 + 分钟级 upsert 修正）。这是避免"窗口聚合无法撤回历史"的务实做法 —— 详见 §4.3。

### 4.3 Exactly-Once 与幂等：结论与理由（D10）

| 层 | 语义要求 | 机制 | 理由 |
|---|---|---|---|
| **ODS** | 精确一次（不能多也不能少） | **Stream Load 2PC**（`sink.enable-2pc=true`，随 checkpoint 提交） | 明细行重复 = 金额翻倍，必须强一致。2PC 的代价是"提交时机绑定 checkpoint"，但 ODS 本来就是延迟 30 s 可接受 |
| **DWD** | 精确一次（同 ODS） | 同 ODS（2PC + Unique Key 兜底） | 清洗是 1:1 映射，2PC 最省事 |
| **DWS** | 幂等（重复算同一分钟结果一样） | **Unique Key 覆盖写**（`dept_id + stat_date + supplier_id`），不做 2PC | 聚合结果由输入唯一决定：重放同一批事件 → 同一结果 → 覆盖无害。用 2PC 反而带来"聚合窗口结果必须等 checkpoint 才可见"的延迟与长事务 |
| **ADS** | 幂等 | 定时（每分钟）从 DWS `INSERT INTO ... SELECT` 覆盖当日分区 | ADS 是"派生视图的物化"，天然可重算 |

**2PC vs 幂等 upsert 的完整对比**

| 维度 | 2PC（Stream Load 两阶段提交） | 幂等 upsert（Unique Key 覆盖） |
|---|---|---|
| 一致性 | Exactly-Once | At-Least-Once + 幂等 = 效果等价 EO |
| 延迟 | 受 checkpoint 间隔约束（30 s） | 可 5 s 一批可见（更实时） |
| 失败恢复 | 必须从最近 checkpoint/savepoint 恢复，否则 label 冲突 | 任意位置重启，覆盖写自动收敛 |
| Doris 侧开销 | 每个 checkpoint 一个事务，事务数 = 作业数 × 频率 | 同量级（批次更小） |
| 适用 | 明细、必须精确的账目 | 聚合、可重算的派生结果 |
| **本设计结论** | **ODS/DWD 用** | **DWS/ADS 用** |

### 4.4 Checkpoint 策略（D11）

```yaml
# flink-conf.yaml 关键项
execution.checkpointing.interval: 30s
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 10min
execution.checkpointing.min-pause: 10s
execution.checkpointing.max-concurrent-checkpoints: 1
execution.checkpointing.tolerable-failed-checkpoints: 3
execution.checkpointing.unaligned.enabled: true          # 反压时不阻塞，避免 checkpoint 超时
execution.checkpointing.externalized-checkpoint-retention: RETAIN_ON_CANCELLATION
state.backend.type: hashmap                              # 无大 keyed state，堆内足够
state.checkpoints.dir: file:///data/flink-checkpoints
state.savepoints.dir: file:///data/flink-savepoints
# 网络/内存（32C/128G 单机，TM 24G）
taskmanager.memory.process.size: 24576m
taskmanager.numberOfTaskSlots: 4
parallelism.default: 2
```

| 决策 | 值 | 依据 |
|---|---|---|
| 间隔 30 s | 大屏"秒级"实际上要靠"30 s 链路 + 前端 30 s 轮询 + Redis 60 s 缓存"，而不是真实时 | 链路延迟预算：Debezium ≤2 s + Kafka ≤1 s + Flink checkpoint 30 s + Doris 可见 ≤5 s ≈ **38 s 上界**，优于"分钟级"要求 |
| 状态后端 hashmap | 作业只有 offset + 1 分钟窗口状态（估算 < 200 MB） | 引入 RocksDB 只增加磁盘 IO 与调优面；第 2 批若出现大 keyed state（如去重 7 天）再切 |
| 存本地目录 | 单机场景 `file://`；方案 B 改 NFS/对象存储 | Flink 2.x 取消了对 `file://` 的强制限制，单机可用；**必须每日 rsync 到备份盘**（§10.2） |
| unaligned | 开启 | 反压时对齐屏障会等到天荒地老，unaligned 是生产必需品 |

### 4.5 作业监控与失败恢复

| 项 | 配置/阈值 | 告警方式 |
|---|---|---|
| 重启策略 | `restart-strategy: fixed-delay`，`attempts=10`，`delay=10s` | 超 10 次失败 → 作业 `FAILED`，告警 |
| Savepoint | 每次作业变更（改 SQL/换 connector 版本）前必须打 savepoint，**文件名带 Git commit** | 脚本 `bin/flink-stop-with-savepoint.sh <job>` |
| 升级流程 | ① savepoint → ② 停旧作业 → ③ 用新 jar/sql 启 → ④ 验证 → ⑤ 记录 commit | 写入 §11 第 ③ 步验收 |
| 关键指标 | `numRestarts`、`lastCheckpointDuration`、`lastCheckpointSize`、各算子 `busyTime`/`backPressuredTimeMsPerSecond`、`numRecordsInPerSecond` 与 Kafka lag 对账 | Prometheus + Grafana（§10.1） |
| 数据对账 | 每 10 分钟：`SELECT count(*) FROM ods_... WHERE dt=CURRENT_DATE` vs PG 侧同日 `count(*)`，差异 >0.1% 告警 | 菜芦 `business/monitor` 展示 |
| 延迟监控 | Kafka 消费者 lag（`kafka-consumer-groups.sh --describe`）+ 端到端延迟（Doris `max(ts_ms)` 与 `now()` 差） | 大屏右上角显示"数据截止时间"，用户可自证新鲜度 |

**故障演练清单（第 ② 步验收必做）**：

| 故障 | 注入方式 | 期望行为 |
|---|---|---|
| Debezium 进程被杀 | `kill -9` | Kafka 无重复；重启后从 offset 继续；Doris 无重复行（2PC label 去重） |
| Kafka broker 重启 | `systemctl restart kafka` | Flink 作业不失败（`fixed-delay` 重连），lag 短时上升后归零 |
| Doris BE 重启 | `systemctl restart doris-be` | Stream Load 失败重试；checkpoint 失败 3 次内自愈 |
| 槽失效（WAL 超限） | 手动停 Debezium + 灌 WAL | PG 不受影响；按 §3.8 SOP 重灌 |
| Flink 作业 OOM | 注入大消息 | `fixed-delay` 重启，checkpoint 恢复，不丢数据 |

### 4.6 与"Flink CDC"（替代 Debezium 直连）的取舍说明

任务书明确要 Debezium → Kafka，这里只记录我们**放弃** Flink CDC 直连的理由，避免评审时被问住：

| 维度 | Debezium → Kafka → Flink（选定） | Flink CDC 直连 PG |
|---|---|---|
| 多消费方 | Kafka 是缓冲与分发中心，BI/ERP/MDM 都能订阅 | 每个 Flink 作业一个复制槽 → 槽数量爆炸（本机实测槽会 pin WAL，槽越多风险越大） |
| 数据回放 | Kafka 保留 7 天，可回放 | 需重新快照 |
| 组件数 | +Kafka（本来就要） | -Kafka（但第 2 批一定会要） |
| 运维 | Kafka 单点/集群需要管 | 少一个组件 |
| **结论** | **第 1 批按任务书用 Debezium+Kafka**；Flink CDC 只在"临时补数"场景作为工具使用（不常驻） | — |

## 5. OLAP 建模（Apache Doris）

### 5.1 为什么是 Doris（D12 的完整论证）

先把"我们的需求"钉死，再比：

| 需求（来自任务书） | 量化 | 对 OLAP 的硬要求 |
|---|---|---|
| 亿级以上数据量 | 5×10⁸~1×10⁹ 行 | 列存 + 分区裁剪 + 向量化 |
| 秒级大屏 | P95 ≤ 2 s | 高并发点查 + 预聚合/MV + 结果缓存 |
| 业务自助取数 | 20~50 并发 | 高并发下延迟稳定（不能一条大查询拖垮全站） |
| 分析师写 SQL | 多表 join（星型） | CBO + 多种 join 策略 |
| 老板固定报表 | 10~30 个固定口径 | 物化视图 + 查询改写 |
| CDC 实时 upsert | 1,200 事件/s 峰值 | **主键模型 + 写时合并（不是查询时去重）** |
| 团队运维能力 | 1~2 人兼职 | 组件少、部署简单、中文文档全 |

**对比表（2026-10 版本，五维 + 许可）**

| 维度 | **Apache Doris 4.0.8** | StarRocks 4.0.x | ClickHouse 26.8 LTS |
|---|---|---|---|
| 实时 upsert | ✅ **Unique Key + Merge-on-Write**，写时标记删除、读时跳过，无查询放大 | ✅ Primary Key 模型（Delete+Insert + 持久化主键索引） | ⚠️ `ReplacingMergeTree` 合并时机不可控，查询需 `FINAL`（同类场景常见 2~10× 降速） |
| 多表 join | ✅ Broadcast / Shuffle / Bucket Shuffle / Colocation 四种策略 + CBO | ✅ 同等能力（Colocate/Shuffle/Broadcast）+ CBO | ⚠️ 历史弱项，需反规范化；新版本（26.8）引入实验性 Cascades 优化器，仍标 experimental |
| 高并发点查 | ✅ 千级并发，行存/点查优化 + SQL Cache（4.0 起默认开） | ✅ 强（pipeline 执行 + query cache） | ⚠️ 一台机器打一条大查询的设计，高 QPS 需靠物化视图+配额硬调 |
| 运维复杂度 | 中（FE + BE 两进程；3.0 起还有存算分离模式可选） | 中（FE + BE/CN，同样两进程） | 中高（需要 Keeper/ZooKeeper 组做副本协调；副本、分区、TTL 调优面大） |
| 中文生态 | ✅ **原百度 Palo 团队，中文文档/社区/商业支持最完整** | ✅ 中文生态也很好（原 Doris 团队分支） | ⚠️ 英文为主，中文资料以社区博客为主 |
| 许可 | Apache 2.0 | Apache 2.0（2022 起） | Apache 2.0 |
| Flink 集成 | ✅ 官方 `flink-doris-connector`（26.2.0 支持 Flink 2.2）+ 2PC | ✅ 官方 connector + stream load | ✅ 官方 connector（但 upsert 语义受限） |
| 本场景结论 | **✅ 选它** | 接近，可作为备选 | ❌ 不选 |

**结论不变，明确推荐 Doris。** 三条决定性理由（不是"中文生态"这种软理由）：

1. **我们要的是"能改的数据"**：采购订单会改状态、物料会改价、供应商会改信息。ClickHouse 的 `ReplacingMergeTree` 在合并前会读到重复行，等于让 BI 层承担"去重正确性"的风险 —— 这在财务口径上是不能接受的。Doris 的 MoW 在写入时就把旧行标记删除，**读到的永远是一个版本**。
2. **我们要 join**：`dws` 层需要 `事实 × 物料 × 供应商 × 部门` 四表关联。ClickHouse 要我们把这些摊平成一张大宽表，摊平后的存储与更新成本更高。
3. **我们是 1~2 人运维**：Doris 单机 `FE+BE` 两条命令起，方案 A 就能跑；ClickHouse 要做副本就得先起 Keeper 组，第 1 批不值得。

> **如果结论可能不同**：若未来本平台的主要负载变成"纯 append 的日志/埋点 + 极少数超大扫描查询"，ClickHouse 会更快更省。**切换成本**：Doris DDL → ClickHouse DDL 需要改模型（Unique Key → ReplacingMergeTree）、改 Flink sink（Doris connector → JDBC/ClickHouse sink）、改 BI 查询生成器（方言）。这个成本约 **8~12 人日**，故第 1 批选型一旦落地，第 2 批内不轻易换。

**版本选择：4.0.8 而不是 4.1.5**

| 版本 | 状态（2026-10） | 选择 |
|---|---|---|
| 4.1.5（2026-10-16） | 最新 | ❌ 上线仅 12 天，缺生产验证 |
| **4.0.8（2026-08-14）** | **官方标 "Stable for production" 的维护版本** | ✅ **选它** |
| 3.1.4（2025-12） | 上一代稳定线 | 备选（回退目标） |

**JDK 要求**：Doris 3.0+ 需 **JDK 17**（与本方案统一的 JDK 17 一致）。

### 5.2 库与表命名规范

| 层 | 库名 | 表名前缀 | 示例 | 生命周期 |
|---|---|---|---|---|
| ODS（贴源明细） | `ods_purchase` / `ods_master` / `ods_mdm` | `ods_` | `ods_purchase_order_line` | 明细保留 90 天（`dynamic_partition` 自动删） |
| DWD（明细清洗） | `dwd_purchase` / `dwd_master` | `dwd_` | `dwd_purchase_order_line` | 保留 2 年 |
| DWS（汇总） | `dws_purchase` | `dws_` | `dws_purchase_dept_day` | 永久（体积小） |
| ADS（应用） | `ads_bi` | `ads_` | `ads_purchase_dept_month_supplier` | 永久 |

**强制规范（写进 review checklist）**

1. 所有表名带层前缀；**禁止跨层直接读**（ADS 只能读 DWS/DWD，DWD 只能读 ODS）。
2. 所有明细表必须有 `dt DATE` 分区列，且**与业务时间同源**（不用 `now()`，否则重灌会错分区）。
3. 所有 `Amount`/`Price` 列用 `DECIMALV3(20,4)` / `DECIMALV3(18,6)`（与菜芦 PG 的 `NUMERIC(20,4)`/`(18,6)` 对齐，避免精度漂移）。
4. 时间列用 `DATETIME(3)`（毫秒），存 UTC+8 本地时间（与菜芦一致，避免 BI 层再换算）。

### 5.3 数据模型逐场景选择（D13）

| 层/表 | 模型 | 理由 | 关键参数 |
|---|---|---|---|
| `ods_purchase_order_line` | **Unique Key（MoW）** | 要按 `id` 覆盖（CDC 更新），且要能删（`op=d`）；明细行 1:1 对应业务主键 | `UNIQUE KEY(id)`，`enable_unique_key_merge_on_write=true` |
| `dwd_purchase_order_line` | **Unique Key（MoW）+ 部分列更新** | 清洗作业只更新自己负责的列（`clean_flag`、`dept_id` 补全），不重写整行 | `enable_unique_key_partial_update=true`，`partial_update_new_key_behavior=APPEND` |
| `dws_purchase_dept_day` | **Unique Key**（不是 Aggregate） | 聚合结果会被"分钟级修正"反复覆盖；Aggregate 模型的 REPLACE 语义在多版本并发下容易出错，Unique 覆盖最直观 | `UNIQUE KEY(dept_id, stat_date, supplier_id)` |
| `ads_purchase_dept_month_supplier` | **Aggregate（SUM/REPLACE）** | 月度汇总只追加、可累加，Aggregate 减少存储与扫描 | `AGGREGATE KEY(stat_month, dept_id, supplier_id)` + `SUM(amount)`、`REPLACE(latest_ts)` |
| ODS 里的"原始 JSON 备份"表 | **Duplicate** | 事件流原始记录，允许重复（用于审计与重放），不需要主键去重 | `DUPLICATE KEY(event_id)` |
| 维表 `dim_material` | **Unique Key（MoW）** | 主数据会变，需按编码覆盖 | `UNIQUE KEY(material_id)`，`replication_num` 按部署形态 |

**逐场景理由（一句话版）**：

- **"数据会被改" → Unique Key**：凡是业务主键存在、且后续会被更新的表，一律 Unique Key（MoW），因为读到的永远是最新一版，BI 层不需要 `GROUP BY` 去重。
- **"数据只追加、且要累加" → Aggregate**：月度汇总就是典型，`SUM` 直接下推到存储层，查询只扫聚合结果。
- **"数据是流水、允许重复" → Duplicate**：审计/重放场景，保留原始事件，重复有助于对账。
- **"部分列更新" 只在 DWD 用**：ODS 是全列镜像（2PC 保证完整），DWD 的多个清洗作业（如"补部门"和"补供应商"分别跑）用部分列更新避免互相覆盖。

### 5.4 分区与分桶：从数字反推（不是拍脑袋）

**输入（第 1 批预估，来自 §1.3 实测行宽 + 任务书量级）**

| 事实 | 值 | 来源 |
|---|---|---|
| 单据行日增 | 1 万行/日（第 1 批）/ 500 万行/日（目标规模） | 任务书 + §5.7 |
| 单行 Doris 存储（压缩后） | ≈ 60~120 B（列存 + ZSTD，按 §1.3 的 377 B/行原始 × 压缩 3~5×） | 实测 PG 行宽 377 B + 文档口径压缩比 |
| 单分区目标体积 | **1~2 GB**（Doris 最佳实践：单 tablet 100 MB~1 GB） | 文档口径 |

**推导（目标规模，日增 500 万行）**

```
日增原始体积 ≈ 5e6 × 377 B         ≈ 1.88 GB
压缩后（/3）  ≈ 0.63 GB/日
单日分区取 1 GB 量级  → 8 桶 → 每 tablet ≈ 80 MB/日  ✅（在 100 MB~1 GB 区间内）
若日增涨到 2000 万行（S3 场景）：
  压缩后 ≈ 2.5 GB/日 → 仍用 8 桶 → 每 tablet 310 MB/日 ✅
  超过 8 GB/日 → 调 16 桶（DDL 支持单分区 ALTER，但建议第 2 批重跑建表）
```

**DWS 表**：`dept(200) × day(3650) × supplier(50)` ≈ 3650 万行，全表压缩后约 **1.4 GB** → 按 **月**分区 + **4** 桶，单 tablet ≈ 30 MB，完全够。

**分桶数上限提醒**：Doris 建议单表 tablet 总数 < 10 万；`90 天 × 8 桶 = 720 tablet`，加 3 副本 = 2,160，远低于上限 ✅。

### 5.5 物化视图：只上 1 个，验证后再铺（D15）

```sql
-- 异步物化视图：月度×部门×供应商（大屏 KPI 与"采购金额趋势"主力）
CREATE MATERIALIZED VIEW IF NOT EXISTS ads_bi.mv_purchase_month_dept_supplier
BUILD IMMEDIATE REFRESH AUTO ON SCHEDULE EVERY 5 MINUTE
DISTRIBUTED BY HASH(dept_id) BUCKETS 4
PROPERTIES ("replication_num" = "1")
AS
SELECT DATE_TRUNC(stat_date, 'month') AS stat_month,
       dept_id,
       supplier_id,

       SUM(amount_sum)  AS amount_sum,

FROM dws_purchase.dws_purchase_dept_day
GROUP BY DATE_TRUNC(stat_date, 'month'), dept_id, supplier_id;
```

| 为什么要 MV | 说明 |
|---|---|
| 大屏 90% 请求打在同一口径 | "本月采购金额 Top10 供应商"、"部门月度趋势" 都基于 `month × dept × supplier` |
| 透明改写 | Doris 的异步 MV 支持查询透明改写（命中则自动改读 MV） |
| 刷新成本可控 | 5 分钟刷新，源表 3,650 万行聚合 ≈ 秒级（Doris 增量刷新，文档口径） |
| 第 1 批只上 1 个 | 先验证"刷新是否稳定、改写是否命中、元数据是否影响 BI 数据集"三件事，再决定第 2 批铺几个 |

**不上的场景**：自助取数的任意维度组合（`dept × 物料类别 × 周`）→ MV 组合爆炸，靠"结果缓存 + workload group 限流"解决，不做 MV。

### 5.6 查询并发能力评估（数字论证，不是"高性能"）

**先说清"并发"指什么**：自助取数场景下的并发 = **同时运行的查询数**（不是 QPS）。一条 90 天 × 21 部门的 DWS 查询扫描 90 万行 ≈ 35 MB 压缩数据（§1.6 实测 900 万行 1.6 GB 的比例外推）。

**单机 32C/128G（方案 A）的估算模型**

```
单查询资源画像（DWS 层，命中分区裁剪）：
  - 扫描量：35 MB 压缩 → 解压后 ~150 MB
  - 单核解压+扫描吞吐（向量化，NVMe）：≈ 200~400 MB/s（文档口径）
  - 单查询 CPU 时间：150 MB / 300 MB/s ≈ 0.5 核·秒
  - 实测 PG 上同类聚合 2.3~17 ms（§1.6）；Doris 列存 MPP 通常快 3~10×，
    保守取"单查询 50~200 ms"（含 FE 解析/调度）

并发上限（CPU 维度）：
  32 核 / 0.5 核·秒每查询 ≈ 64 查询/秒 的"CPU 秒容量"
  若 P95 目标 2 s，单查询占用 0.5 核·秒 → 32 核可支撑 32×2/0.5 ≈ 128 并发（纯算力）
  减去 FE 解析、Doris 后台 compaction、Flink 导入 → 打 25% 折扣 ≈ 96

工程结论（不是理论值）：
  - 图形化取数（数据集预定义，走 MV/缓存）：**30~50 并发** 稳定，P95 < 1 s
  - 自助取数（自由维度组合）：**20 并发** 稳定，P95 1~3 s
  - 分析师 SQL（大范围扫描）：**4 并发**，超时 60 s 强制 kill
  - 超过上述 → 进入队列（workload group queue），而不是拖慢所有人
```

**Workload Group 配置（直接可用）**

```sql
-- 图形化取数（BI 数据集查询，走 MV/缓存，并发高但单查询轻）
CREATE WORKLOAD GROUP IF NOT EXISTS wg_bi_dashboard
PROPERTIES (

    "max_queue_size" = "80",

    "memory_limit" = "40%",

);

-- 自助取数（自由组合维度，中等重量）

PROPERTIES (
    "max_concurrency" = "20",
    "max_queue_size" = "40",
    "queue_timeout" = "10000",
    "cpu_soft_limit" = "30%",
    "memory_limit" = "30%",
    "tag" = "bi_adhoc"
);

-- 分析师 SQL 工作台（大查询，严格限流）

PROPERTIES (
    "max_concurrency" = "4",
    "max_queue_size" = "4",
    "queue_timeout" = "3000",
```

### 5.7 容量账（第 1 批 vs 目标规模，实测常量外推）

| 项 | 第 1 批（S1：存量 3000 万 / 日增 10 万行） | 目标规模（S2：存量 5 亿 / 日增 500 万行） | 极端（S3：存量 10 亿 / 日增 2000 万行） |
|---|---|---|---|
| 增量事件/日 | 252,000（≈3 事件/s，峰值 23/s） | 12,502,000（**145 事件/s，峰值 1,158/s**） | 60,005,000（695/s，峰值 5,556/s） |
| WAL 生成 | 0.18 GB/日 | **9.2 ~ 10.2 GB/日**（月 280~305 GB） | 44 ~ 52 GB/日（月 1.3~1.6 TB） |
| Kafka 原始量（Avro 前） | 0.11 GB/日 | 5.29 GB/日 | 25.4 GB/日 |
| Kafka RF=3 + 7 天保留 | 2 GB | **111 GB** | 533 GB |
| Kafka 峰值带宽 | 0.01 MB/s | **0.5 MB/s** | 2.4 MB/s |
| Doris 单副本（ODS+DWD+DWS） | **4 GB** | **38 GB** | 75 GB |
| Doris 3 副本 | 11 GB | 115 GB | 225 GB |
| 4T NVMe 占用估算（含 Kafka、checkpoint、临时文件 2× 余量） | < 50 GB（**1.3%**） | ≈ 350 GB（**9%**） | ≈ 1.3 TB（**33%**） |

**结论**：

1. **第 1 批的硬件需求被严重高估了** —— 4 T 盘只用到 1~9%，32C/128G 的算力上限远高于 1,158 事件/s 的吞吐。真正的瓶颈不是容量，是 **Doris 的查询并发与 compaction 后台开销**。
2. **Kafka 峰值 0.5 MB/s 是"玩具级"负载** —— 单 broker 完全够；上三节点是为了可用性，不是为了吞吐。
3. **WAL ≈ 10 GB/日** 是唯一需要盯紧的数：它决定了 `max_slot_wal_keep_size=4GB` 只能容忍"槽卡住约 9~10 小时"。**这个时间窗口就是运维的响应 SLA**（§10.1 告警要求 15 分钟内响应）。

## 6. 数据湖（第一批只做最小决策）

### 6.1 结论：第 1 批 **不上** MinIO + Paimon/Iceberg（D16）

| 论点 | 依据 |
|---|---|
| **① 容量不需要** | §5.7：S2 目标规模下 Doris 3 副本 115 GB，4T 盘占用 9%。湖的价值是"低成本存海量原始数据"，而我们的原始明细只有 38 GB 级 |
| **② 组件数 +3** | MinIO（对象存储）+ 表格式（Paimon/Iceberg）+ 元数据服务（Hive Metastore 或 REST Catalog）。第 1 批是"1 条管道 + 1 个仪表盘"，加 3 个组件意味着 3 份新的运维面、3 份新的故障模式 |
| **③ 场景未出现** | 湖的典型价值：Spark/Python 大规模跑批、跨引擎共享（Trino/Flink/Doris 共读一份数据）、原始数据留存 > 1 年。第 1 批三个都不需要 |
| **④ 技能不匹配** | 团队是 Rust 后端 + 前端，Java 生态本就在"必要时才碰"的定位（§12.1）；再叠一层表格式（Paimon 的 changelog、Iceberg 的 manifest/snapshot）会显著拉高门槛 |
| **⑤ Doris 已提供"准湖"能力** | Doris 4.x 原生支持 Iceberg/Paimon/Hive Catalog 只读查询（4.1 支持 Iceberg 读写、Paimon 只读；**Paimon 写入要 4.2**）。真到需要时，Doris 侧几乎零改造接入 |

### 6.2 触发条件（任一满足即启动第 2 批湖方案评估）

1. **原始明细保留 > 1 年**（合规/审计要求），Doris 存储成本超过对象存储 3 倍；
2. 需要 **Spark/Python 生态**跑算法（特征工程、模型训练），Doris 的 SQL 表达不了；
3. 出现**第二个查询引擎**（Trino/StarRocks）需要与 Doris 共读同一份明细；
4. Doris 单表超过 **50 亿行**且扩容成本高于对象存储方案。

### 6.3 如果第 2 批要上：Paimon vs Iceberg 对比 + 推荐

| 维度 | **Apache Paimon** | Apache Iceberg |
|---|---|---|
| 与 Flink 的关系 | ✅ **Flink 社区主导**，原生流式写入、changelog 产出、LSM 结构支持高频 upsert | ✅ 支持 Flink 写，但流式语义与 upsert 性能不如 Paimon |
| Upsert 能力 | ✅ 强（主键表 + LSM，为流式更新设计） | ⚠️ 支持（v2 行级删除 + v3 deletion vector），CDC 场景写入放大更明显 |
| 流读（changelog） | ✅ 原生 | ⚠️ 需 incremental scan / 版本读，语义更绕 |
| 多引擎读 | ⚠️ Doris 3.1+ 可读、4.2 才可写；Trino 支持 | ✅ **生态最广**（Doris/Trino/Spark/Flink/StarRocks 全支持，读写） |
| 小文件治理 | ✅ LSM 天然合并 | ⚠️ 需定期 `rewrite_data_files` 维护 |
| 成熟度（2026-10） | 1.x，Flink 生态首选 | 事实标准，多引擎共享首选 |
| **推荐** | **若第 2 批的目标是"Flink 流式入湖 + Doris 查询"，选 Paimon** | **若目标是"多引擎共享一份明细（Spark + Trino + Doris 都读）"，选 Iceberg** |

**本设计的推荐（若触发）**：**Paimon**，理由是"我们的写入方永远只有 Flink，读取方主要是 Doris" —— 这个组合正好是 Paimon 的主场；等到需要多引擎共享时，Doris 4.2+ 的 Paimon 写支持也已成熟。

## 7. BI 服务层（自研，菜芦 Rust 侧）

### 7.1 设计原则（5 条，决定了后面所有细节）

1. **前端永不提交 SQL 片段**：只提交「数据集编码 + 维度/度量编码 + 过滤器（字段编码 + 操作符 + 值）」。SQL 由服务端从白名单拼装。
2. **标识符来自数据库，值来自参数绑定**：`column_name` 只能来自 `bi_dataset_field`（已入库的白名单），值一律 `?` 绑定 —— 这是防注入的唯一可靠做法（字符串转义永远有坑）。
3. **权限在 SQL 生成之后、执行之前注入**：行级范围与列级脱敏作为"查询计划改写器"的最后一道，任何绕过（如 SQL 工作台）也必须过这道。
4. **一查询一审计**：`bi_query_log` 记录 `sql_text`、指纹、耗时、扫描行数、命中缓存 —— 这是后续"慢查询治理"与"数据权限审计"的唯一事实源。
5. **大查询不能拖垮业务 API**：BI 用**独立连接池 + 独立 workload group + 独立超时**，三重隔离（见 §2.3 与 §7.5）。

### 7.2 数据模型（9 张 BIOS 表，已在 PG 18.6 真库验证，DDL 见附录 C）

|---|---|---|
| `bi_dataset` | 数据集 = 逻辑表 → Doris 物理表 | `uk_bi_dataset_code`、`ck_bi_dataset_rows/timeout/cache` |
| `bi_dataset_field` | **字段白名单唯一来源** | `uk_bi_field_column(dataset_id, column_name)`；`ck_bi_field_role_agg`（measure 必须有聚合函数） |

**SQL 生成算法的 6 条硬规则（对应 D17）**

| # | 规则 | 实现 | 拦截的注入方式 |
|---|---|---|---|
| R1 | 表名/列名**只能**来自 `bi_dataset`/`bi_dataset_field` 的已入库值，且再校验字面量正则 `^[a-z_][a-z0-9_]{0,63}$` | 查库 → 校验正则 → 拼入 | `"; DROP TABLE"`、注释注入 |
| R2 | 值一律 `?` 绑定（`Vec<DorisValue>`），**永不拼接** | `sqlx` 风格的参数化 | `' OR 1=1--`、UNION 注入 |
| R3 | 聚合函数只允许枚举集 `{sum,count,avg,max,min,count_distinct}` | 枚举映射，不是字符串直传 | `sum(x)--` 之类的表达式注入 |
| R4 | `order_by` 字段必须在 SELECT 列表里（别名或维度/度量编码） | 别名映射表 | 任意列探测 |
| R5 | `limit` 强制 `min(user_limit, dataset.max_rows)`，且必须 `>0` | 服务端截断 | 无 LIMIT 大结果集打爆内存 |
| R6 | 过滤操作符枚举 `{=,!=,>,>=,<,<=,in,not_in,between,like,is_null}`，`like` 只允许右模糊（`value%`） | 枚举 + 值处理 | `like '%...'` 全表扫 |

**生成的 SQL 示例（含行权限注入后的最终形态）**

```sql
-- 服务端生成（?: 为绑定参数）
SELECT `stat_date` AS `stat_date`,
       `supplier_id` AS `supplier_id`,
       SUM(`purchase_amount`) AS `amount`
FROM `dws_purchase`.`dws_purchase_dept_day`
WHERE `stat_date` BETWEEN ? AND ?
  AND `supplier_id` IN (?, ?, ?)
  /* ---- 行级权限注入（来自 bi_row_scope，见 §7.4）---- */
  AND `dept_id` IN (?, ?, ?, ... , ?)          -- 21 个绑定参数，上限 500
ORDER BY `amount` DESC
LIMIT 500;
```

**指标表达式（`bi_dataset_metric.expression`）怎么保证安全**：不是自由文本。规则是 `聚合函数(白名单列)` 或 `白名单列 算术运算 白名单列`，服务端用一次性解析器（Rust：`nom` 手写 20 行递归下降，或 `sqlparser` 解析后遍历 AST 校验），只接受 `Column`/`AggregateFn`/字面量节点；出现子查询、函数调用（除白名单）即拒绝。**不引入完整 SQL 解析器**（`sqlparser` 主要用于第 2 批的 SQL 工作台白名单校验，见 §7.5）。

**Rust 侧模块结构（在 AGENTS.md"四件套"约定下的最小扩展）**

```
backend/src/business/bi/
├── mod.rs          # 模块声明 + 初始化（Doris 池 + 数据集元数据预热）
├── handler.rs      # 对外 HTTP 入口（#[alun::get/post] + #[alun::permission]）
├── dto.rs          # 请求/响应结构（serde + validator）
├── model.rs        # bi_dataset / field / metric / perm / scope / mask / dashboard 的数据访问
└── query/          # ← 对"四件套"的最小扩展：查询引擎的内部实现
    ├── mod.rs
    ├── pool.rs     # Doris 独立连接池（Db::connect_with，与全局 PG 池隔离）
    ├── builder.rs  # 6 条规则的 SQL 生成器
    ├── perm.rs     # 行级/列级权限解析与改写
    └── cache.rs    # Redis 结果缓存
```

> 说明：AGENTS.md 要求"每模块四件套、不设 service 层"。查询构建器不是"service 层"（不编排业务事务），而是**纯函数式的 SQL 编译/改写工具**，放 `query/` 子目录并只被 `handler`/`model` 调用。此扩展需在代码评审时显式豁免一次，理由写在 `mod.rs` 顶部注释里。

**handler 骨架（对齐现有 `business/monitor` 的写法）**

```rust
//! BI 模块（二开模块 business/bi）
//!
//! | 方法 | 路径 | 权限码 |
//! |------|------|--------|
//! | POST | /business/bi/dataset/query | business:bi:dataset:query |
//! | GET  | /business/bi/dataset/list  | business:bi:dataset:list  |
//! | POST | /business/bi/sql/execute   | business:bi:sql:execute   |
//! | GET  | /business/bi/dashboard/:code | business:bi:dashboard:view |
//!
//! 写法与 business/monitor 完全一致：路由宏路径不含 /api（前缀由 [router] prefix 注入），
//! 权限由 #[alun::permission] 声明（与 sys_menu.auth_code 一一对应，SUPER_ADMIN 短路）。
use alun::prelude::*;

#[alun::permission(
    path = "/business/bi/dataset/query",
    method = "POST",
    permission = "business:bi:dataset:query"
)]
#[alun::post("/business/bi/dataset/query")]
pub async fn query_dataset(
    Extension(AuthClaims(claims)): Extension<AuthClaims>,
    ValidatedJson(req): ValidatedJson<DatasetQueryReq>,
) -> ResResult<DatasetQueryRes> {
    let user_id = utils::current_user_uuid(&claims);                  // 底座工具（与 support/config 一致）
    let ds      = model::load_dataset(&req.dataset_code).await?;      // 元数据（Redis 缓存 60s）
    let scope   = query::perm::resolve_row_scope(user_id, &ds).await?; // 行级权限（Redis 缓存 300s）
    let masks   = query::perm::resolve_masks(user_id, &ds).await?;    // 列级脱敏
    let (sql, params) = query::builder::build(&ds, &req, &scope, &masks)?;
    // 缓存键含 scope 签名 + 数据集版本：行权限不同的人绝不会共用到彼此的结果
    if let Some(hit) = query::cache::get(&ds, &sql, &scope).await? { return Ok(hit); }
    let result = query::exec_with_timeout(&sql, params, ds.timeout_secs).await?;
    model::log_query(user_id, &ds, &sql, &result).await?;             // 审计
    query::cache::put(&ds, &sql, &scope, &result, ds.cache_ttl_secs).await?;
    Ok(result)
}
```

### 7.4 数据权限落地（D18/D19，本设计的核心难点）

#### 7.4.1 行级权限：查询改写（不是视图、不是 Doris Row Policy）

**三种方案的对比（决策依据）**

| 方案 | 实现 | 优点 | 致命缺点 | 结论 |
|---|---|---|---|---|
| **A. Doris 视图**（每角色/每数据集一个视图） | 为每个 `(role, dataset)` 建视图，视图里写死 `WHERE dept_id IN (...)` | DB 层强制，绝对安全 | 视图数 = 角色数 × 数据集数（10 角色 × 20 数据集 = 200 个视图，且角色变更要重建 DDL）；**动态变动（用户换部门）无法自动跟随** | ❌ |
| **B. Doris Row Policy** | `CREATE ROW POLICY ... TO ROLE r USING (dept_id IN (...))` | DB 层强制 | 需要把菜芦角色/部门**同步成 Doris 角色**（双份账号体系）；`root/admin` 免疫策略；策略按角色而非按"部门子树"表达，子树要枚举 | ❌ 第 1 批不用（第 2 批可作为"深度防御"叠加） |
| **C. 查询改写（选定）** | 菜芦解析用户部门子树 → 注入 `dept_id IN (?,?,…)` → 参数绑定执行 | 动态（换部门立即生效）、一处实现（数据集/大屏/SQL 工作台共用）、可审计 | 依赖"所有查询都过菜芦"这条纪律 | ✅ **选它** |

**为什么 C 是安全的**：因为**最终用户拿不到 Doris 账号**（§10.3）——所有访问都必须经过菜芦，菜芦是唯一入口。这是 C 成立的前提，必须写进运维红线。

**子树解析算法（`dept_path` 前缀，实测最快）**

```sql
-- ①  查用户所属部门（sys_user.dept_id），拿到 dept_path
SELECT dept_path FROM sys_dept WHERE id = $1;

-- ②  一次查出整个子树（前缀匹配，走 idx_sys_dept_path）
SELECT id FROM sys_dept
WHERE dept_path LIKE $1 || '%' AND status = 1 AND deleted_at IS NULL;

-- ③  scope_type 处理
--     ALL              → 不注入条件（但仍注入 row_filter_sql 基线）
--     DEPT             → 只注入自己的 dept_id
--     DEPT_AND_CHILD   → 注入 ② 的结果集
--     SELF             → 注入 user_id 对应维度（如 create_by = ?）
--     CUSTOM           → bi_row_scope.dept_ids 数组（人工挑选，上限 200）
```

**性能依据（§1.6 实测）**：21 个部门的子树在 100 万行 DWS 上耗时 2.33 ms（走 `dept_id` 前缀索引），**权限过滤成本可忽略**。因此本设计不为行权限做任何预聚合 —— 只需要把"子树解析"缓存 300 s。

**边界情况（必须实现）**

| 情况 | 处理 |
|---|---|
| 用户 `dept_id` 为空 | 只返回 `SELF` 范围（`create_by = user_id`）；无 `SELF` 规则则拒绝（403） |
| 子树部门数 > 500 | 不拼 `IN`，改为 `dept_id IN (SELECT dept_id FROM bi_perm_dept_snapshot WHERE role_id=? AND batch_no=?)`（第 2 批能力；第 1 批直接拒绝并提示"权限范围过大，请缩小部门"） |
| 数据集 `dept_column` 为空（如公共维度表） | 不做行级过滤，但**必须是 `bi_dataset.row_filter_sql` 里显式声明的公共数据集**，且 `sensitive_level=0` |
| 多角色用户 | **并集**（`OR` 合并），且 `can_query` 任一为真即可查 |
| 超级管理员 | 跳过行级过滤，但**仍写审计日志**（"超管查看全量数据"必须留痕） |

#### 7.4.2 列级脱敏：SQL 表达式替换 + 结果集二次脱敏（双保险）

```sql
-- 生成 SQL 时，若该字段对当前角色需脱敏：
SELECT
  `supplier_id`,
  CONCAT(LEFT(`contact_phone`, 3), '****', RIGHT(`contact_phone`, 4)) AS `contact_phone`
FROM ...
```

| 层 | 做法 | 拦截什么 |
|---|---|---|
| SQL 层 | 字段表达式替换为脱敏函数（`LEFT/RIGHT/CONCAT`、金额区间化 `CASE WHEN amount < 10000 THEN '1万以下' ...`） | 图形化取数、数据集查询 |
| 结果集层 | 服务端在返回前按 `mask_policy` 再过一遍（只处理"仍未脱敏且策略要求脱敏"的列） | 分析师用 `concat`/`substr` 绕过 SQL 层脱敏 |

**审计**：`bi_query_log` 记录"本次查询涉及 N 个脱敏字段"（放 `sql_text` 的注释里或单独字段，第 2 批加 `masked_fields JSONB`），供合规抽查。

### 7.5 分析师 SQL 工作台：7 道闸门（对应 D21）

| # | 闸门 | 实现 | 拒绝时的行为 |
|---|---|---|---|
| G1 | **只读账号** | Doris 用户 `analyst_ro`，只有 `SELECT_PRIV`（库级），无 `LOAD/ADMIN/GRANT` | 权限错误直接透出 |
| G2 | **语句类型白名单** | 用 `sqlparser` 解析：只允许单条 `SELECT`（含 `WITH`）；禁止 `INSERT/UPDATE/DELETE/DDL/LOAD/EXPORT/SET/KILL` | 400 `SQL_NOT_ALLOWED` |
| G3 | **库表白名单** | 解析出的每个表引用必须在 `bi_dataset`（或 `dws_*/ads_*/dwd_*` 白名单前缀）里；禁止 `ods_*` 与系统库（`__internal_schema`、`mysql`） | 400 `TABLE_NOT_ALLOWED` |
| G4 | **强制 LIMIT** | 无 `LIMIT` 或 `LIMIT > max_rows` → 外层包一层 `SELECT * FROM (原SQL) t LIMIT N` | 静默改写 + 响应标 `truncated=true` |
| G5 | **超时** | 会话 `SET query_timeout=60`；菜芦侧 `tokio::time::timeout(65s)` 双保险 | 504 `QUERY_TIMEOUT` |
| G6 | **资源组** | `SET workload_group='wg_analyst_sql'`（§5.6：并发 4、CPU 硬限 20%） | 排队超时 → 429 `TOO_BUSY` |
| G7 | **行级权限** | **同样过 §7.4.1 的改写器**：如果 SQL 引用了含 `dept_column` 的表，必须在 WHERE 里注入 `dept_id IN (...)`（用 AST 改写：找到主表的 `TableFactor`，在 `WHERE` 前 AND 一个 `Expr::InList`） | 无法安全注入（如自连接/子查询多层）→ 500 `CANNOT_APPLY_ROW_SCOPE`（宁拒绝不放过） |

> **G7 是最容易被忽略的一条**：SQL 工作台如果不做行级注入，等于分析师一个人绕过了所有数据权限。**第 1 批实现范围**：只支持"单表 + 简单 JOIN（JOIN 表都是公共维表）"的 AST 注入；复杂查询（CTE/窗口/自连接）直接拒绝并提示"请改用数据集取数"。这个保守策略是正确的取舍。

**工作台额外能力（第 1 批给最小集）**：SQL 保存（复用 `bi_query_log` 不适合，第 2 批加 `bi_saved_sql` 表）、执行历史（查 `bi_query_log WHERE query_source='SQL_WORKBENCH'`）、结果导出 CSV（限 5 万行，走流式响应，不落盘）。

### 7.6 结果缓存（D20）

```rust
// 缓存键 = sha256(数据集版本 | 规范化SQL | 行权限签名 | 角色脱敏签名)
// 规范化：去空白、参数占位化、统一大小写关键字 → 同义查询命中同一缓存
fn cache_key(ds_ver: u32, sql_norm: &str, scope_sig: &str, mask_sig: &str) -> String {
    let mut h = Sha256::new();
    h.update(format!("{}|{}|{}|{}", ds_ver, sql_norm, scope_sig, mask_sig));
    hex(h.finalize())
}
```

| 项 | 设计 | 理由 |
|---|---|---|
| **键必须含权限签名** | `scope_sig` = 排序后的 `dept_id` 列表哈希 | 否则 A 部门用户会看到 B 部门缓存的数字（**自研 BI 最经典的数据泄漏 bug**） |
| **键必须含数据集版本** | `bi_dataset.version`（字段/指标变更时 +1） | 改了指标口径，旧缓存必须失效 |
| TTL 分级 | 大屏 60 s / 固定报表 300 s / 自助取数 60 s（可配 0） / SQL 工作台 **不缓存** | 大屏要"看起来实时"，报表要"稳定" |
| 存储 | 复用菜芦 `cache` 门面（生产 `type="redis"`），key 前缀 `bi:q:`，单值上限 **1 MB**（超过不缓存，防大结果集打爆 Redis） | 现有 `[cache]` 配置零改造 |
| 击穿 | 单飞（single-flight）：同一 key 并发只放 1 个真实查询，其余等待（进程内 `DashMap<String, Notify>`） | 大屏 30 台终端同时刷新 → 只打 1 次 Doris |
| 雪崩 | TTL 加 **±10% 抖动** | 避免整点集体失效 |
| 主动失效 | `bi_dataset` 更新时按前缀删（Redis `SCAN bi:q:*` + 版本号已变自然失效，双保险） | MV 刷新后可选"清空当日 key" |

### 7.10 连接池与限流的数字（第 1 批）

| 资源 | 配置 | 依据 |
|---|---|---|
| 菜芦 → Doris 连接池 | `max_connections=20`、`min=2`、`acquire_timeout=5s`、`max_lifetime=1800s` | Doris 单查询 50~200 ms；20 连接 × 5 QPS ≈ 100 QPS 上限，远高于实际（10 屏 × 每 30 s 一次 ≈ 0.3 QPS，20 人自助取数 ≈ 2 QPS） |
| 每请求超时 | 图形化 30 s / 自助 60 s / SQL 工作台 60 s / 大屏 15 s | 大屏要快速失败并展示"数据获取超时"，不能卡住 30 s |
| 全局并发保护 | 菜芦侧 `Semaphore(16)`（每实例）+ Doris `workload group`（§5.6） | 应用层削峰 + DB 层兜底 |
| 单用户限流 | 每用户 5 次/秒查询（复用底座 `rate_limit` 中间件配置，规则化到 `/business/bi/*`） | 防误操作狂点 |

**查询链路的延迟预算（大屏，P95）**

| 环节 | 预算 | 实测/口径 |
|---|---|---|
| 前端 → 菜芦（内网） | 5 ms | 内网 |
| 菜芦：解析请求 + 加载数据集元数据（Redis 命中） | 3 ms | Redis P95 < 1 ms × 3 次 |
| 菜芦：行权限解析（Redis 缓存 300 s） | 2 ms | 命中缓存 |
| 菜芦：SQL 生成 | < 1 ms | 纯内存 |
| 缓存命中 → 直接返回 | 10 ms | **大部分请求在这里结束** |
| 缓存未命中 → Doris 执行（DWS 表，分区裁剪 + MV） | 50~300 ms | §5.6 推算 |
| 结果集序列化（500 行 × 6 列） | 3 ms | |
| **合计（命中缓存）** | **≈ 20 ms** | 满足"秒级" |
| **合计（未命中）** | **≈ 60~320 ms** | 满足 P95 < 2 s 要求 |

## 8. MDM（主数据管理，菜芦侧）

### 8.1 定位与本批边界

**MDM 是独立主数据平台，不是 ERP 的一个模块。** 它管"任意主数据域"（物料/供应商/客户/部门/仓库/科目…），向下兼容外部系统（ERP/WMS/手工 Excel），向上通过 API/事件把权威数据分发给所有消费方。

**第 1 批只做物料（`material`）一个域的最小闭环**：

```
域建模 → 属性定义 → 编码规则 → 录入/导入 → 去重（精确+模糊）→ 疑似队列
  → 人工确认 → 合并（含 unmerge）→ 提交 → 审核 → 发布 → 分发（Kafka/Webhook/Pull）
```

**不做**：域设计器（可视化拖拽建模）、数据分级分类、主数据质量评分、跨域血缘、外部系统反向同步（ERP 改了要回写 MDM —— 第 2 批）。

### 8.2 数据模型（9 张表，已在 PG 18.6 真库验证）

| 表 | 作用 | 关键设计 |
|---|---|---|
| `mdm_domain` | 域定义 | `biz_key_column`/`name_column` 声明哪个属性是业务键与名称；`lifecycle` 决定审核态（`DRAFT_ONLY` 二态 / `TWO_LEVEL` 两级） |
| `mdm_attribute` | 属性定义 | `data_type`/`is_required`/`is_unique`/`is_key`（参与匹配）/`enum_values`/`value_regex`/`min|max`/`match_weight`/`mask_policy` |
| `mdm_code_rule` | 编码规则 + 取号 | `prefix + period_key + lpad(current_seq)`；单语句原子取号（**实测 480 并发 0 重号，§1.8**） |
| `mdm_record` | 主数据记录 | **关键列下沉**：`record_code`/`record_name`/`status`/`version`/`is_merged`/`merged_into` 为列；其余属性 `attrs JSONB` + GIN 索引 |
| `mdm_record_alias` | 编码别名 | 被合并/改码后的旧编码 → 权威记录（**业务系统引用不断链**） |
| `mdm_match_rule` | 匹配规则 | `EXACT`/`FUZZY`/`NORMALIZED` + `attr_codes` + `normalizer` + `threshold` + `auto_merge` |
| `mdm_duplicate` | 疑似重复队列 | `(left_record, right_record)` 唯一 + `ck_mdm_dup_order`（left < right 防重复对） |
| `mdm_merge_log` | 合并/拆分审计 | `snapshot` 存合并前全量（unmerge 恢复依据）+ `field_winner` 记录逐字段裁决来源 |
| `mdm_publish` / `mdm_change_event` / `mdm_subscription` | 发布 / 变更事件 / 订阅登记 | 事件表是分发的唯一事实源，复用同一条 CDC 管道 |

**迁移号段**：`business/` **V0049–V0059**（BI 占 V0040–V0048，§7.2）。

### 8.3 域建模：属性定义的能力边界

| 能力 | 第一批支持 | 实现 |
|---|---|---|
| 属性类型 | string / number / date / datetime / bool / enum | `mdm_attribute.data_type` |
| 必填校验 | ✅ | `is_required`，服务端校验（错误码 `MDM_REQUIRED_MISSING`） |
| 唯一性校验 | ✅（域内） | `is_unique` + 应用层校验 + `mdm_record` 唯一索引兜底 |
| 值域（枚举） | ✅ | `enum_values JSONB`：`["PCS","KG","M"]` |
| 正则格式 | ✅ | `value_regex`（如物料编码 `^[A-Z0-9\-]{4,40}$`，实测拦截通过） |
| 数值区间 | ✅ | `min_value`/`max_value` |
| 参与去重匹配 | ✅ | `is_key` + `match_weight`（0~1，用于模糊匹配加权） |
| 脱敏显示 | ✅ | `mask_policy`（复用 §7.4.2 的策略枚举） |
| 属性级权限 | ❌ 第 2 批 | 第 1 批用"属性脱敏"近似 |
| 层级/引用属性（如供应商→地区） | ❌ 第 2 批 | 第 1 批用 string + 值域 |

**编码规则（3 个必须钉死的约定）**

1. **格式**：`前缀 + 周期 + 流水`，如 `M` + `202610` + `000001` = `M202610000001`。
2. **周期**：`date_pattern` 决定重置节奏（`YYYYMM` 月度重置，`YYYY` 年度，`NONE` 不重置）。周期切换由取号语句自动处理（`period_key` 变更时 `current_seq` 归零）。
3. **不释放**：编码一旦占用即永久占用（合并/停用不释放，见 §8.4 铁律 3），只有软删（`deleted_at`）后可回收 —— 这是审计要求。

### 8.4 去重与合并（本批最复杂的一块）

#### 8.4.1 匹配：两层

| 层 | 手段 | 阈值 | 动作 | 性能 |
|---|---|---|---|---|
| **精确匹配** | 归一化后（`TRIM/UPPER/去空格/全角转半角`）`record_code` 或 `biz_key` 相等 | 1.0 | **直接拒绝新增**（提示"编码已存在"） | 唯一索引，O(1) |
| **规范化匹配** | 归一化 `name` + `spec` 组合相等（`REMOVE_SPACE`：`六角螺栓M8*30` ≡ `六角螺栓 M8*30`） | 1.0 | 入"疑似重复"队列（`score=1.0`），人工确认 | `pg_trgm` GIN，毫秒级 |
| **模糊匹配** | `pg_trgm similarity()` + `match_weight` 加权（名称 0.6 + 规格 0.4） | ≥ 0.85 入队；≥ 0.95 可配 `auto_merge` | 入队 / 自动合并（默认关闭） | `pg_trgm` GIN 索引，10 万级主数据 < 100 ms |

```sql
-- 模糊匹配候选集（GIN 索引 + trigram，避免全表相似度计算）
SELECT r.id, r.record_code, r.record_name,
       similarity(r.record_name, $1) AS name_sim
FROM mdm_record r
WHERE r.domain_id = $2
  AND r.deleted_at IS NULL AND r.is_merged = FALSE
  AND r.record_name % $1              -- 走 gin_trgm_ops，先粗筛
ORDER BY name_sim DESC
LIMIT 20;
```

> **归一化的价值（实测案例）**：`六角螺栓 M8*30 不锈钢` vs `六角螺栓M8*30  不锈钢`（多余空格）+ 规格 `M8*30` vs `M8X30` —— 归一化后 `name` 完全相等，走"规范化匹配"直接入队 `score=1.0`；不做归一化则要靠模糊匹配得 0.86，人工判断成本更高。

#### 8.4.2 合并：三条铁律（第 3 条来自真库验证发现的缺陷）

| # | 铁律 | 原因 |
|---|---|---|
| **铁律 1** | **合并保留"权威记录"，其余记录标记 `is_merged=true, merged_into=<权威ID>`，绝不物理删除** | 物理删除后无法 unmerge、无法追溯"这条数据曾经存在" |
| **铁律 2** | **被合并方的编码必须写入 `mdm_record_alias`**（`alias_type='MERGED'`），解析接口先查 `record` 再查 `alias` | 业务系统（ERP 历史单据）里存的是旧 ID/旧编码，别名表保证"旧引用仍能解析到权威记录" |
| **铁律 3** | **编码一旦使用即不释放**：`uk_mdm_rec_code` 只带 `deleted_at IS NULL` 条件，**不带 `is_merged`** | 初版设计"合并后释放编码"会让 unmerge 恢复时与新记录撞唯一键（实测复现：`duplicate key value violates unique constraint "uk_mdm_rec_code"`）；修正后 unmerge 顺利恢复 |

**冲突字段裁决（`field_winner`）**：合并时逐属性决定取值来源，规则优先级：

```
① 显式人工指定（前端逐字段选择"用 A 的/用 B 的"）
② 数据源权威度：MDM 手工 > ERP > WMS > 导入
③ 非空优先（A 为空则用 B）
④ 更新时间最新
⑤ 兜底：保留权威记录的值
```

裁决结果写 `mdm_merge_log.field_winner = {"spec": "<A的id>", "name": "<B的id>"}`，unmerge 时按此还原"哪部分来自谁"。

**unmerge（拆分）**：从 `merge_log` 取最近一次 `MERGE` 的 `snapshot` → 恢复被合并记录的 `is_merged=false, merged_into=NULL, status=PUBLISHED` → 删除对应 `alias` → 写一条 `UNMERGE` 日志。**实测验证通过**（`record_code=M202610000001, status=PUBLISHED, is_merged=f`）。

**状态机（第一批，二态）**

```
        ┌──────── 驳回 ────────┐
        ▼                      │
    DRAFT ──提交──► PENDING ──审核通过──► APPROVED ──发布──► PUBLISHED
        ▲                      │                              │
        │                      └──(lifecycle=TWO_LEVEL)─► 二级审核
        └──────────────── 停用 ◄──────────────────────── OBSOLETE
```

- `DRAFT_ONLY`（默认）：`PENDING → 审核 → APPROVED → 发布 → PUBLISHED`（**一次审核**）
- `TWO_LEVEL`：`PENDING → 部门审核 → 中心审核 → APPROVED`（`audit_level` 记 0/1/2，第二次通过后 `audit_level=2`）
- **不做**流程引擎、不做会签/或签/条件分支/动态审批人 —— 审批流引擎已放弃，第 1 批就这两条路径。

### 8.5 订阅分发：三条通道，一套事件源

```
                    ┌─────────────────────────────┐
   业务动作 ───────►│ mdm_change_event (PG 表)     │
   (发布/合并/停用)  └──────────────┬──────────────┘
                                   │ Debezium 捕获（同一条 CDC 管道）
                                   ▼
                     Kafka: cdc.public.mdm_change_event_v1
                     ├──► ERP 消费（Kafka consumer，MDM 物料 → ERP 本地只读副本）
                     ├──► BI/Doris 消费（Flink → dim_material，供报表 join）
                     └──► WMS/其他（同上）
                    
   兜底通道：
   ├── WEBHOOK：菜芦在事务提交后异步 POST 到订阅方（配 secret 签名），失败重试 5 次
   └── PULL：订阅方按 mdm_subscription.last_seen_id 增量拉 GET /api/business/mdm/changes?since=
```

| 通道 | 适用 | 延迟 | 一致性 | 第 1 批是否启用 |
|---|---|---|---|---|
| **Kafka 事件** | 系统间实时同步（ERP/WMS/BI） | 秒级 | 至少一次 + 消费端幂等（按 `record_id + version` 去重） | ✅（复用 CDC 管道，零额外组件） |
| WEBHOOK | 少量外部系统（无法连 Kafka） | 秒级 | 至少一次 + 签名校验 | ✅（只实现，不接外部） |
| PULL | 批处理/夜间对账/初始化 | 分钟~小时 | 最终一致（位点表） | ✅ |

**事件 payload（幂等键 = `record_id + version`）**

```json
{
  "event_id": 10231,
  "domain": "material",
  "record_id": "0f8a…",
  "event_type": "MERGE",
  "version": 7,
  "payload": {
    "code": "M202610000002", "name": "六角螺栓M8*30 不锈钢",
    "attrs": {"spec": "M8*30", "unit": "PCS", "tax_rate": 0.13},
    "aliases": ["M202610000001"],
    "status": "PUBLISHED"
  },
  "published_at": "2026-10-28T10:00:00+08:00"
}
```

> 消费方必须按 `record_id` upsert，并把 `aliases` 写进本地别名表（这样 ERP 里历史单据上的旧编码也能 join 到新物料）。

### 8.6 与 ERP 主数据的关系：**MDM 权威，ERP 订阅**（D24）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. MDM 权威 + ERP 订阅**（选定） | 编码唯一、去重集中、跨系统一致；新增系统（WMS/MES）零改造接入 | MDM 必须先于 ERP 可用（依赖前置）；ERP 开发要接受"主数据只读" | ✅ |
| B. ERP 自管 + MDM 汇总 | ERP 开发简单（自己建表自己写） | **两套编码**：ERP 一套、MDM 一套，必须有映射表；对账永远对不齐；第 2 批接 WMS 时矛盾爆炸 | ❌ |
| C. 双写（两边都可改） | 谁都不依赖谁 | 冲突解决 = 无解；合并/去重无法实施 | ❌ 绝不 |

**落地边界（写进 ERP 开发规范）**

| 事项 | 规则 |
|---|---|
| 物料主数据表 | ERP 建 `biz_material` **只读副本**（来自 MDM 事件），字段与 MDM 对齐；ERP 可加"本地扩展表" `biz_material_ext`（如默认仓库、安全库存） |
| 新增物料 | **只能**在 MDM 里新增 → 发布 → ERP 收到事件后建副本；ERP 页面"新增物料"按钮改为"跳转 MDM" |
| 物料编码 | ERP 不可生成、不可修改（DB 层用触发器或权限拒绝 `UPDATE code`） |
| 停用/合并 | MDM 发布 → ERP 标记 `status=0` / 更新别名映射 |
| 对账 | 每日 02:00 比对 MDM 与 ERP 的物料数量与编码集合，差异 >0 告警（§9.2 质量规则复用） |
| 第一批的依赖顺序 | `MDM 物料域最小闭环` 必须先于 `ERP 物料 CRUD`（§11 排期已体现） |

**这条决策的代价（诚实说明）**：ERP 开发多了一个外部依赖（MDM 未发布 → ERP 无法建物料），第 1 批联调会痛。**缓解**：MDM 提供"种子数据导入"（Excel → 批量建 → 一键全量发布），保证 ERP 开工前物料字典已就位。

## 9. 数据治理（第一批最小集）

### 9.1 元数据：表/字段说明 + 负责人

### 9.2 数据质量：4 类规则 + 告警

| 类型 | 规则 | 检验 SQL（示例，跑在 Doris） | 阈值 | 告警级别 |
|---|---|---|---|---|
| **空值率** | 关键字段非空率 < 99% | `SELECT SUM(CASE WHEN dept_id IS NULL THEN 1 ELSE 0 END)/COUNT(*) FROM dwd_purchase_order_line WHERE dt = CURRENT_DATE` | > 1% | P2 |
| **唯一性** | 主键重复 | `SELECT COUNT(*) - COUNT(DISTINCT id) FROM ods_purchase_order_line WHERE dt = CURRENT_DATE` | > 0 | **P1** |
| **值域** | 枚举越界 | `SELECT COUNT(*) FROM dwd_purchase_order_line WHERE status NOT IN ('DRAFT','APPROVED','RECEIVED','CLOSED') AND dt = CURRENT_DATE` | > 0 | P2 |
| **及时性** | 数据延迟 | `SELECT (UNIX_TIMESTAMP(NOW()) - MAX(src_ts_ms)/1000) FROM ods_purchase_order_line` | > 600 s | **P1** |
| **对账** | 行数一致 | Doris 当日行数 vs PG 当日行数（跨库，菜芦侧执行两条 SQL 比对） | 差异 > 0.1% | **P1** |

**实现（第 1 批不引入 Great Expectations / DolphinScheduler）**：

```yaml
# /opt/bigdata/quality/rules/purchase_line.yaml（Git 管理）
- code: dq_purchase_line_unique
  name: 采购订单行主键唯一
  target: ods_purchase.ods_purchase_order_line
  sql: SELECT COUNT(*) - COUNT(DISTINCT id) AS bad FROM {table} WHERE dt = '{date}'
  expect: bad = 0
  severity: P1
  owner: bi-team
- code: dq_purchase_line_freshness
  name: 采购订单行及时性
  target: ods_purchase.ods_purchase_order_line
  sql: SELECT (UNIX_TIMESTAMP(NOW()) - MAX(src_ts_ms)/1000) AS lag_sec FROM {table} WHERE dt = '{date}'
  expect: lag_sec < 600
  severity: P1
```

- **调度**：复用菜芦底座 `plugins.scheduler`（`support/sys_job`）—— 每 10 分钟跑一次，结果写 `bi_query_log` 的同款审计表（第 2 批独立 `dq_result` 表；第 1 批先写日志 + 告警）。
- **告警**：P1 → 企微/钉钉群 + 站内通知（底座 `notification` 插件，`plugins.notification.enabled`）；P2 → 只在"数据质量"页面展示。
- **第一批只做 5 条规则**（上表），跑通"规则 → 执行 → 告警 → 处置"闭环，再谈扩到 50 条。

### 9.3 血缘：第一批做表级，用"登记式"（D25）

| 方案 | 实现 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. ETL 登记（选定）** | Flink 作业的 SQL 文件头写 `-- @source: ods_purchase_order_line -- @target: dwd_purchase_order_line`，CI 脚本解析注释生成 `lineage_edge` YAML，菜芦展示 | 100% 准确（作业就是血缘）、零运行时开销、可在 CI 拦截"未登记血缘的作业" | 靠规范（有人不写就漏） | ✅ **第 1 批** |
| B. 解析 SQL | 用 `sqlparser` 解析作业 SQL 提取 source/target | 自动化 | Flink SQL 方言 + 自定义 connector 容易解析失败；`INSERT INTO ... SELECT` 之外的形式（CTAS、视图）覆盖不全 | 第 2 批（与 SQL 工作台共用解析器） |
| C. 运行时采集（hook Flink） | 拦截 catalog 访问 | 全自动 | 侵入 Flink 运行时，升级风险大 | ❌ |

**表级血缘的存储（第 1 批用 YAML + 菜芦展示）**

```yaml
# /opt/bigdata/jobs/lineage.yaml（CI 由 SQL 文件头注释生成，人工可补）
edges:
  - {from: "pg:public.biz_purchase_order_line", to: "kafka:cdc.public.biz_purchase_order_line_v1", job: "debezium"}
  - {from: "kafka:cdc.public.biz_purchase_order_line_v1", to: "doris:ods_purchase.ods_purchase_order_line", job: "flink/01_ods_sync.sql"}
  - {from: "doris:ods_purchase.ods_purchase_order_line", to: "doris:dwd_purchase.dwd_purchase_order_line", job: "flink/02_dwd_clean.sql"}
  - {from: "doris:dwd_purchase.dwd_purchase_order_line", to: "doris:dws_purchase.dws_purchase_dept_day", job: "flink/03_dws_agg.sql"}
  - {from: "doris:dws_purchase.dws_purchase_dept_day", to: "bi:dataset:purchase_amount_trend", job: "bi"}
```

菜芦"数据地图"页读这份 YAML（或第 2 批入库），支持"表 → 上游/下游"双向查看。**第 1 批的价值**：改表前能查到"谁在用"（避免删字段炸 BI）。

### 9.4 指标字典：口径统一的唯一落点

| 要素 | 存放 | 强制字段 |
|---|---|---|
| 指标编码 | `bi_dataset_metric.metric_code` | `purchase_amount_total`（全局命名规范：`{域}_{对象}_{动作}`） |
| 指标名称 | `metric_name` | 采购金额合计 |
| **业务口径** | `caliber_desc` | **必填**，写清"含税/去税、含退货、按单据日期还是收货日期" |
| 技术表达式 | `expression` | `sum(purchase_amount)`（受控表达式，§7.3） |
| 单位/精度 | `unit` / `precision` | 元 / 2 |
| 负责人 | `bi_dataset.owner_user_id` | 必填 |

**治理流程（第 1 批靠"制度"而非工具）**

1. 新指标必须先在指标字典登记，才能被仪表盘引用（`bi_dashboard_widget.query_spec` 只允许引用已登记指标码）。
2. 口径变更走"新增版本"（第 2 批加 `bi_dataset_metric.version` + 生效日期），**禁止直接改 `expression`**（否则历史报表数字会"偷偷变"）。
3. 每月一次"指标口径评审"（业务 + 数据负责人），差异写入 `caliber_desc` 的变更记录。

> **为什么指标字典对 BI 是生死线**：同一个"采购金额"，采购部算"含税下单价"、财务算"去税入账价"，两个仪表盘给出两个数 → 老板不再相信任何报表。**这件事靠工具解决不了，只能靠"唯一登记 + 口径必填 + 版本化"的制度设计 + 系统强制。**

### 10.3 账号体系与权限映射（关键安全决策）

**核心结论：最终用户永远拿不到 Doris 账号**（这是 §7.4 行级权限成立的前提）。

| 账号 | 在哪 | 权限 | 谁用 | 密钥管理 |
|---|---|---|---|---|
| `cailu`（菜芦应用） | PG | 业务库读写 | 菜芦后端 | 环境变量 `ALUN_DATABASE_*` |
| `cdc_reader` | PG | `LOGIN REPLICATION` + 3 张表 `SELECT` | Debezium | 环境变量 |
| `flink_writer` | Doris | `LOAD_PRIV` on `ods_purchase/dwd_purchase/dws_purchase/ads_bi`（**无 SELECT，无 DDL**） | Flink sink | 环境变量 |
| `bi_reader` | Doris | `SELECT_PRIV` on `dwd_*/dws_*/ads_*`（**无 ods_***，无写） | 菜芦 BI 查询池 | 环境变量 / 配置中心 |
| `analyst_ro` | Doris | `SELECT_PRIV` on 白名单库（同 `bi_reader`，但走独立连接池与 `wg_analyst_sql`） | 菜芦 SQL 工作台 | 同上 |
| `doris_root` | Doris | 全权 | **仅运维，日常不使用**，密码在密码管理器 | 离线保管 |

**菜芦角色 ↔ Doris 权限的映射规则**

```
菜芦 sys_role（业务概念）  ──►  菜芦应用层判定（bi_dataset_perm / bi_row_scope / bi_column_mask）
                                  │
                                  ▼
                        三个固定 Doris 账号（bi_reader / analyst_ro / flink_writer）
```

- **不做**"每个菜芦角色建一个 Doris 角色"：那是双份权限体系，任何一次人员调动都要改两处，第 2 批必然不一致。
- **不做**"每个用户一个 Doris 账号"：Doris 有连接数与元数据开销上限，且密码管理成本高。
- **第 2 批的深度防御（可选）**：在 Doris 侧对 `dws_*` 建 Row Policy（按 Doris 角色），把"菜芦 SQL 生成 bug 导致越权"的风险再挡一层 —— 但**前提**是角色同步自动化，否则不做。

**审计三件套**

| 审计对象 | 落点 | 保留 | 内容 |
|---|---|---|---|
| 查询行为 | `bi_query_log`（菜芦 PG） | 180 天 | 谁、查了哪个数据集、SQL 指纹、耗时、返回行数、是否脱敏 |
| MDM 变更 | `mdm_merge_log` + `mdm_publish` + `mdm_change_event` | 永久 | 合并/拆分/发布的操作人、原因、快照 |
| 权限变更 | 底座 `operation_logs`（中间件自动） | 180 天 | 数据集授权、行级范围变更 |

### 10.4 传输加密与网络安全

| 链路 | 加密 | 第 1 批要求 |
|---|---|---|
| 浏览器 → 菜芦 | HTTPS（反向代理终止 TLS） | ✅ 必须 |
| 菜芦 → Doris（9030） | Doris 支持 SSL；内网可先明文 + 网络隔离 | ⚠️ 第 1 批内网明文，第 2 批开 SSL（`useSSL=true` + 证书） |
| Flink → Doris（8030 Stream Load） | 同上 | ⚠️ 同上 |
| Debezium → PG（5432） | `sslmode=require`（PG 开 SSL） | ✅ 建议开（`pg_hba` 已限制源 IP） |
| Debezium → Kafka（9092） | SASL/PLAIN + TLS | ⚠️ 第 1 批内网 + ACL，第 2 批上 SASL |
| 内网隔离 | 大数据机只开放 §2.4 端口表；PG 只对大数据机 IP 开放 5432 | ✅ 必须 |

> **诚实说明**：第 1 批"内网明文"是有意的取舍（少一层证书运维），前提是**大数据机与菜芦机在同一可信网段**且端口按表收敛。若部署在公网可及的机房，第 1 批就必须上 TLS。

### 12.1 关于"双技术栈"的诚实评估（任务书明确要求）

| 维度 | 菜芦（Rust） | 大数据（Java/Scala） | 冲突与对策 |
|---|---|---|---|
| 语言/生态 | Rust 1.94 / axum / sqlx；编译期安全 | JVM 17 / Flink / Kafka / Doris | **两套 CI**、两套依赖管理、两套排障工具链 |
| 部署 | 单二进制（`cargo build --release`） | 多 JVM 进程 + 配置文件 + `lib/` 下的 jar | 菜芦可"扔一个文件就跑"，大数据侧必须脚本化（§11.1） |
| 升级节奏 | 随业务迭代（周级） | 季度级（大版本一年 2~3 次） | **必须划定"数据平台变更窗口"**（如每月第一个周末），不允许随业务随时升 |
| 人才 | 现有团队 | 需要 1 人懂 JVM 调优/Flink 运维 | **现实做法**：现有 1 人兼职 + 文档化运维手册 + 商业支持兜底；不要指望"Rust 工程师顺手把 Flink 调好" |
| 边界成本 | 菜芦不碰集群（D1）→ 这个成本被隔离在"大数据平台"一侧 | 大数据侧不需要懂 Rust | **D1 的边界设计就是为这条风险服务的** |

**一句话结论**：双栈成本真实存在，估算 **3~5 人日/月**；能把它压住的三件事是 **版本锁定 + 全脚本化 + 监控先行**，而不是"招个大数据专家"（第 1 批的量级撑不起专职岗位）。

## 结语：这份设计的三条主线

1. **边界比技术更重要。** 菜芦管"人、口径、权限、配置"，大数据平台管"怎么流、怎么算、怎么存"，两边用 MySQL 协议 + Kafka 事件通信，谁也不托谁的生命周期（D1/D2）。这条线一旦模糊，运维成本会指数上升。
2. **防护比优化更重要。** 复制槽的 WAL 堆积（实测复现）、BI 行级权限的缓存串数据、SQL 工作台的大查询拖库 —— 这三件事任何一件出错都会让平台"上线即事故"。第八、七、三章占了全文近一半篇幅，原因就在这里。
3. **诚实比漂亮更重要。** 43 人日、3~5 人日/月的双栈成本、Doris 性能数字未实测、144 不能跑 Doris、5 条降级预案 —— 这些都写在纸上。**设计文档的价值不在于显得完备，而在于让读到它的人在出问题时有路可走。**
