# 会话吊销的耐久性边界（CODE-16 B）

> 适用范围：`backend/src/system/auth/handler.rs`（登录 / 刷新 / 登出）、
> `backend/src/middleware/auth_guard.rs`（吊销复检）、
> `backend/src/support/online/model.rs`（在线会话与 refresh 登记）。
> 相关配置：`backend/config/config.toml`、`docker/docker-compose.prod.yml`。

## 1. 结论先说

令牌吊销（登出 / 强制下线 / 改密 / 停用 / 改角色）的真实性由**三样东西分层保证**：

| 层 | 载体 | 覆盖的东西 | 缓存全丢时是否还成立 |
|----|------|-----------|----------------------|
| ① `ver` claim ↔ `sys_user.token_version` | **PostgreSQL** | 该用户**全部**已签发令牌（access + refresh） | ✅ 成立（不依赖缓存） |
| ② 用户软删 / 停用 | **PostgreSQL** | 会话主体不存在即 401 | ✅ 成立 |
| ③ 黑名单 / 轮换血缘 / 在线会话 | **Redis** | 单条令牌的即时失效、一次性 refresh、复用检测 | ❌ 不成立（一次性保证退化为统计保证） |

也就是说：**「改密 / 停用 / 改角色后旧令牌立刻失效」是库侧强保证**；
**「旧 refresh 令牌只能兑换一次」是缓存侧保证**，缓存丢失或淘汰时它会退化。
本文件说明退化的边界、为什么可接受、以及运维上必须守住什么。

## 2. 吊销状态具体存在哪

| 键 | 值 | TTL | 写入者 | 语义 |
|----|----|-----|--------|------|
| `token:blacklist:{jti}` | `true` | 令牌剩余有效期 | 登出、强制下线、轮换作废旧 refresh | 该 jti 立刻失效 |
| `token:rotated:{jti}` | `{sid, at}` | 旧 refresh 剩余有效期 | 刷新轮换成功后 | 该 refresh **已被用过**（判复用的唯一依据） |
| `token:replay:{jti}` | 本次签发的令牌对 | 60 秒 | 刷新轮换成功后 | 60s 内重放同一旧令牌 → 原样回放（跨标签页幂等） |
| `online:token:{access jti}` | 在线会话快照 | access 剩余有效期 | 登录 / 刷新 | 在线用户列表 + 强制下线枚举依据 |
| `online:refresh:{refresh jti}` | `{user_id, sid, exp}` | refresh 剩余有效期 | 登录 / 刷新 | 强制下线能枚举到 refresh（B7 补的缺口） |

框架自身的认证层也会查 `token:blacklist:{jti}`，但它是 **fail-open** 的
（`alun-web 0.4.2` `middleware/auth.rs`：`if let Ok(Some(_)) = Cache::get(..)`，读失败即放行）。
因此项目侧加了 `App::route_layer` 的复检层（`middleware/auth_guard.rs`）：
**查不到 = 拒绝**（401 + `error` 日志）。缓存不可用期间，带令牌的请求全部被拒，
不存在「吊销名单读不到但仍放行」的窗口。

## 3. 缓存丢失 / 淘汰时，具体退化成什么样

假设 Redis 被清空、被淘汰、或换了新实例（`online:*` 与 `token:*` 一起消失）：

| 场景 | 退化后的状态 | 真实影响 |
|------|-------------|----------|
| 用户已登出，但 Redis 被清空 | 旧 access 在 `exp` 前重新可用；旧 refresh 能再次兑换 | 直到 access 过期（≤15 分钟）或用户下次登录 |
| 管理员停用 / 改密 / 改角色 | **不受影响**：`token_version` 自增 + 会话主体校验在库里，下一次请求即 401 | 无 |
| 旧 refresh 被复用（泄露） | `token:rotated` 丢失 → 复用检测失效，最坏退化为「旧 refresh 可再兑换一次」 | 一次性保证退化为统计保证 |
| refresh 被强制下线 | 库里 `ver` 不匹配 → 刷新路径同样 401 | 无 |

## 4. 为什么这个边界可以接受

1. **access TTL 已经从 2 小时压到 15 分钟**（`access_token_expire_secs = 900`）。
   即使彻底失去吊销名单，单条 access 的暴露窗口也只有 15 分钟——这就是把
   「缓存是统计保证」变成可接受风险的那个几何因子。
2. **改密 / 停用 / 改角色走库侧，不依赖缓存**：`ver` claim 逐请求比对
   （`middleware/session_guard.rs`）+ 刷新路径比对（`handler.rs`）。这类「最需要
   立刻生效」的吊销与缓存健康无关。
3. **一次性 refresh 的退化有一道上限**：绝对上限是 `siat + refresh_ttl`（24 小时，
   轮换不滑动）。就算攻击者抢到一条旧 refresh，他最多也只能在这个窗口里用它，
   而且一旦正常客户端用它刷新，复用检测会把整条会话杀掉。
4. **写侧失败不再静默**：吊销写不进去时，接口回 5xx
   （用户管理侧有库侧兜底，故按可接受降级处理并记 `error` 日志；角色 / 菜单这类
   纯靠缓存收回权限的入口直接回 500）。

## 5. 运维必须守住的四件事

### 5.0 TTL 必须在**每个 profile** 里各写一遍

`alun-config 0.4.2` 的 `merge_middleware` 判定是：

```rust
if overlay.auth.access_token_expire_secs != 0 { base.auth.access_token_expire_secs = overlay.auth.access_token_expire_secs; }
```

而 profile 文件里**缺**该字段时，serde 填的是编译期默认值 `7200`（≠ 0），于是：

- `config/config.toml` 写成 `900` 也**会被 profile 的默认值盖掉**（实测 `print-config` 仍输出 `7200/604800`）；
- 只改基础配置 = 什么都没改。

因此 TTL 在 `config.toml` **和** `config-{dev,prod,test}.toml`（含两份 `.example` 模板）里都写了一遍。
验证方法：

```bash
cd /opt/cailu/backend && set -a && . /etc/cailu/cailu-dev.env && set +a
./target/debug/cailu print-config | grep expire_secs      # 期望 900 / 86400
```

### 5.1 `cache.type` 必须是 redis（prod / dev）

`config/config.toml` 的 `[cache] type = "local"` 只是兜底值：进程内 LRU 缓存**重启即清空、
多实例不共享**，用它等于把上述退化变成常态。因此启动守卫
（`shared/startup_guard.rs::check_cache_backend`）在 profile 为 `prod` / `dev`
且 `cache.type != "redis"` 时**直接拒绝启动**，并打印含危害说明的 FATAL 日志。

### 5.2 `--maxmemory-policy` 必须是 `noeviction`

`docker/docker-compose.prod.yml` 里已经改成 `noeviction`。**不要改回 `allkeys-lru`**：

- 淘汰 = 黑名单 / 轮换标记失效 = 已登出、已被强制下线的令牌重新可用（吊销静默失效）；
- 轮换标记丢失还会让「一次性 refresh」退化成可重放。

`noeviction` 下内存写满时写入会失败，后端把这些失败回传给调用方（5xx），
是可观测的失败而不是静默的降级。

### 5.3 Redis 内存水位监控阈值

吊销键都很小（黑名单 `true`、轮换标记 ~60 字节、refresh 登记 ~120 字节），
按并发在线用户数估算：`10 万在线 × (1 access + 1 refresh) ≈ 30–40 MB`，
512 MB 上限留有 10 倍余量。但必须有告警兜住「异常流量 / 键泄漏」：

| 指标 | 告警阈值 | 处置 |
|------|---------|------|
| `used_memory / maxmemory` | 持续 **> 70%** 预警 | 查 `INFO keyspace` 的键数量与增长曲线 |
| `used_memory / maxmemory` | 持续 **> 85%** 严重 | 立刻扩容或清理非吊销类键；此水位下写入可能开始被拒 |
| `redis_commands_processed` 中 `OOM` 错误 | **> 0 即告警** | 说明已经在丢吊销写入（接口会回 5xx） |
| `evicted_keys` | **必须恒为 0** | 非 0 说明 `noeviction` 没生效或被改回 LRU |

采集方式：`redis-cli INFO memory` / `redis-cli INFO stats`（或容器内
`docker exec cailu-prod-redis redis-cli INFO`）。

### 5.4 多实例与缓存重启

- 多实例**必须共享同一个 Redis**（`ALUN_REDIS_URL` 指向同一实例、不同 db 需谨慎）：
  黑名单只在写入方可见时，其它实例照放行。
- Redis 重启后 `token:*` 与 `online:*` 全空。此时库侧 `ver` 仍然拦得住改密 / 停用 /
  改角色，但「已登出的 refresh」会重新可用直到绝对上限。**升级 / 重启 Redis 属于
  安全事件**，须记录在变更单里，必要时配合 `token_version` 自增（管理端「强制下线」）。

## 6. 复用检测（一次性 refresh）的完整链条

一次刷新请求的判定顺序（顺序本身是设计，勿调）：

```
validate  → token_type == Refresh → 绝对上限(siat) → token:replay（60s 幂等回放）
          → token:rotated（命中 = 复用 → 杀会话）→ token:blacklist（登出/强踢）
          → 写 blacklist(旧) → 轮换签发 → 写 rotated + replay + online:refresh(新) → 删旧登记
```

- **60 秒宽限**是为了跨标签页并发刷新：前端单飞只在单标签页内生效
  （`frontend/src/api/request.ts`），没有宽限时第二个标签页的请求会被判复用、
  整条会话被杀（正常用户被踢下线）。
- **判复用的动作**：注销该用户全部会话（access + refresh）+
  `auth_logs`（`REFRESH_TOKEN/FAIL`，`REUSE_DETECTED`）+ `security_logs`
  （`REFRESH_TOKEN_REUSE`）+ 401 `AUTH_TOKEN_REVOKED`。

## 7. 已知边界（不在本卡范围）

- **cookie / CSRF / TLS（A 方案）未做**：令牌仍在 localStorage，XSS 可直接读；
  `docker/frontend/nginx.conf` 目前只 `listen 80`，TLS 是 A 方案的前置阻断项。
- **`token_version` 是用户级粒度**：它让「该用户全部令牌失效」，无法只踢一个设备。
  需要按设备吊销时用 `force_logout`（单条 jti）而不是自增版本号。
