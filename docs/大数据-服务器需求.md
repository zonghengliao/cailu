# 菜芦大数据平台 —— 服务器与基础设施需求

> 建立：2026-10-28 ｜ 依据：数据量亿级 · 秒级实时 · 自助分析+分析师SQL · 独立 MDM 平台 · 自研 BI
> 用途：采购/开机器时的硬件与软件规格依据

## 一、先说三条硬约束（不满足会直接卡死）

| # | 要求 | 原因 |
|---|---|---|
| **1** | **必须 x86_64 架构** | 现有 144 是 aarch64（Parallels VM）。Doris/Flink/Kafka/MinIO 虽部分支持 ARM，但**生态、镜像、调优资料极不完整**，踩坑成本高。新机器一律 x86_64 |
| **2** | **数据盘必须 NVMe SSD** | OLAP 查询性能 80% 吃磁盘 IO。SATA SSD 能跑但慢 3-5 倍；HDD 基本不可用（除了对象存储冷数据） |
| **3** | **网络至少万兆** | Flink/Kafka/Doris 节点间 shuffle 与副本同步极大吃带宽。千兆会成为瓶颈 |

**其他**：Ubuntu 22.04 / 24.04 LTS（server 版，无桌面）；独立公网或内网固定 IP；ESSD/NVMe 云盘优先选本地盘（云盘 IO 有上限）。

## 二、三档配置（按验证 → 生产 → 高可用）

### 方案 A｜验证型 · 一体机（1 台）

> 适用：先跑通全链路、验证架构、小规模压测。**能扛亿级数据的查询，但无容灾**

| 项 | 规格 |
|---|---|
| CPU | **32 核**（x86_64，支持 AVX2） |
| 内存 | **128 GB** |
| 系统盘 | 500 GB NVMe SSD |
| 数据盘 | **4 TB NVMe SSD**（Doris 数据 + Flink checkpoint + Kafka） |
| 网络 | 万兆 |
| OS | Ubuntu 24.04 LTS x86_64 |
| 部署 | 全部组件单机（Kafka KRaft + Flink + Doris 单 FE/BE + MinIO + 调度 + 菜芦应用） |

**预算参考**：云厂商 32C128G + 4T NVMe，约 3000-5000 元/月；自建约 3-5 万一次性。

---

### 方案 B｜生产型 · 3 台（推荐）

> 适用：正式上线、亿级数据、秒级实时、7×24 运行。节点故障可恢复（副本机制）

| 节点 | 角色（软件） | CPU | 内存 | 磁盘 | 网络 |
|---|---|---|---|---|---|
| **node-master** | Kafka Broker + DolphinScheduler + 菜芦应用(Rust) + PG + Redis + **Doris FE** | 16 核 | **64 GB** | 系统 500G SSD + 数据 1T NVMe | 万兆 |
| **node-worker-1** | **Doris BE** + **Flink TaskManager** | 32 核 | **128 GB** | 系统 500G SSD + 数据 **4T NVMe** | 万兆 |
| **node-worker-2** | **Doris BE** + **Flink TaskManager** + **MinIO** | 32 核 | **128 GB** | 系统 500G SSD + **4T NVMe** + 4T HDD（对象存储） | 万兆 |

**要点**：
- Doris 数据按副本 2-3 副本计算，4T 单节点有效容量约 2-3T，够亿级（压缩后）
- Flink TaskManager 与 Doris BE 混部可行，但要给 Flink 限制内存（`taskmanager.memory.process.size`）
- MinIO 在 3 台时只能单副本或 2 副本，非生产级；数据湖正式化后建议独立 4 节点

---

### 方案 C｜高可用 · 5-6 台（数据湖正式化后）

| 节点组 | 数量 | 每台规格 | 说明 |
|---|---|---|---|
| Doris FE（3 副本） | 3 | 16C/64G/1T SSD | 元数据集群，奇数节点 |
| Doris BE | 3 | 32C/128G/4T NVMe | 数据分片，可横向扩 |
| MinIO（纠删码 EC:4+2） | **4**（最少） | 16C/64G/8T HDD + 500G SSD | 纠删码最少 4 节点，容量利用 66% |
| Kafka（3 副本） | 3 | 16C/64G/2T NVMe | 复用 FE 节点亦可 |
| 计算（Flink + Trino） | 2 | 32C/128G/1T SSD | 独立计算池，按需扩 |

## 三、软件栈（我推荐的组合）

| 层 | 选型 | 理由 |
|---|---|---|
| **数据接入** | **Debezium**（PG 逻辑复制 → Kafka） | 零侵入、秒级捕获业务库变更，不用改菜芦代码 |
| **消息队列** | **Kafka 3.x（KRaft 模式）** | 免 ZooKeeper，运维简单 |
| **流计算** | **Apache Flink 1.18+** | 秒级实时 ETL、窗口聚合、Exactly-Once |
| **OLAP** | **Apache Doris 2.1+**（推荐） | 支持**主键模型 upsert**（实时更新）、物化视图（查询加速）、高并发点查；Flink Connector 一等公民；中文社区好。**比 ClickHouse 更适合"实时更新+高并发"，比 StarRocks 更中庸** |
| **数据湖** | **MinIO + Apache Paimon**（Flink 原生）或 Iceberg | Paimon 与 Flink 天然一体，支持流式入湖 + 快照；Iceberg 生态更广（Trino/Spark 都能读） |
| **联邦查询** | **Trino**（可选，用于查湖/跨源） | 只在需要"直查数据湖"时上 |
| **调度** | **DolphinScheduler 3.x** | 中文、可视化 DAG、支持 Shell/SQL/Flink 任务 |
| **BI（自研）** | **菜芦内自研**：Vue3 + ECharts 5 + 查询构建器 + 仪表盘编排 | 按老大要求，**不用 Superset**；好处是完全贴合 TDesign/莫兰迪风格、权限统一在菜芦 |
| **MDM** | **菜芦内自研独立模块** | 主数据域建模、去重合并、审批发布、订阅分发 |
| **元数据/治理** | 首期自研轻量（表级血缘 + 质量规则）；后期可接 DataHub/Atlas | 首期不引重组件 |

## 四、与菜芦的关系（架构边界）

```
┌────────────────────────────────────────────────┐
│ 菜芦应用层（144 或 master 节点）                 │
│  · 业务后台（ERP 等）                            │
│  · MDM 主数据模块（自研）                        │
│  · BI 前端（自研，ECharts）                      │
│  · 数据源/任务/仪表盘管理 API                     │
└───────────────┬────────────────────────────────┘
                │ SQL (Doris 协议) / HTTP
┌───────────────▼────────────────────────────────┐
│ 大数据平台（独立服务器）                          │
│  Debezium → Kafka → Flink → Doris               │
│                      └→ MinIO + Paimon (湖)     │
│  DolphinScheduler 调度                          │
└────────────────────────────────────────────────┘
```

- **大数据平台独立部署**，菜芦**不试图接管 Flink/Kafka 集群生命周期**（只做"数据源登记 + 任务触发 + 查询"）
- 菜芦只通过 **Doris MySQL 协议 / HTTP API** 读取结果；不直接操作 HDFS/对象存储
- 好处：大数据平台可以独立升级/扩容，不影响业务系统

## 五、容量与性能估算（亿级数据）

| 项 | 估算 |
|---|---|
| 原始数据 | 1 亿行 × 200 字节 ≈ **20 GB**（未压缩） |
| Doris 压缩后 | 约 **3-5 GB**（列存 + 高压缩比，通常 4-8 倍） |
| 明细 + 聚合 + 副本 2 | 约 **20-30 GB** 实际占用 |
| 日增量 100 万行/天 | 一年累积 3.6 亿行 ≈ 70-100 GB（含副本与索引） |
| **4T 单节点 × 2 节点 ≈ 5-8T 有效** | **足够支撑 3-5 年**（亿级到十亿级量级） |

**结论**：方案 B（3 台，4T NVMe × 2）对"亿级 + 秒级"是够的，留了充足余量。

## 六、采购优先级建议

1. **必买**：方案 B 的 3 台（或先买 1 台验证型跑通，再补 2 台）
2. **强烈建议**：万兆交换机（内网），否则上述架构性能打折
3. **可选后补**：独立 MinIO 4 节点（数据湖正式化时）
4. **不要买**：Hadoop/HDFS 集群（已被对象存储 + 表格式取代，不必走老路）

## 七、如果只能买 1 台（最小起步）

**32 核 / 128 GB / 系统 500G SSD + 数据 4T NVMe / 万兆 / Ubuntu 24.04 x86_64**

单机可跑：Kafka(KRaft) + Flink + Doris(单FE单BE) + MinIO + DolphinScheduler + 菜芦应用。
验证阶段完全够用，后续加 2 台即升级为方案 B。
